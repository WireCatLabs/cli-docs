Пусть ИИ-агент работает с вашим сайтом на WordPress через `wordpress`, а решение о том, что станет публичным,
остается за вами. Пароль приложения может то же, что ваш пользователь в WordPress, поэтому без ваших собственных
ограничений агент мог бы то же самое.

Для каждого профиля, имени, которое вы дали входу на один сайт, вы решаете, что агент может только читать, что
сначала спрашивает вас и что выполняется сразу. Одной строкой вы оставляете публикацию за собой и знаете, какие
проверки действуют при любых настройках.

У каждой команды есть ключ разрешения, ее имя, например `posts.publish` или `api.media-delete`, или группа, например
`api`, причем более длинный ключ важнее. У каждого ключа есть уровень: `deny`, `readonly`, `ask` или `allow`. Их
задает `wordpress blog config set`.

## Уровни

| Уровень | Что происходит |
|---|---|
| `deny` | Команда отклоняется, даже чтение. |
| `readonly` | Чтение работает. Изменение отклоняется. |
| `ask` | Изменение сначала спрашивает в терминале. Без терминала оно отклоняется, если не передан `--yes`. **Через MCP оно выполняется.** |
| `allow` | Команда выполняется без вопроса. |

```sh
wordpress blog config set permissions.posts.publish deny   # nothing goes public from this profile
wordpress blog config set permissions.api readonly         # every api operation reads, none writes
wordpress blog config show                                 # each key with its level and where it came from
```

`blog` это профиль, имя, которое вы выбрали. Отказ приходит как `permission_error` (код выхода 5) и называет ключ.
Он не значит, что вход сломан.

Агент не может ослабить разрешение: `config set` или `config unset`, которые сняли бы ограничение, отклоняются, если
вы не запускаете их сами в терминале.

## Что задано до ваших изменений

| Ключ | Встроенный уровень | Кто его проверяет |
|---|---|---|
| `posts.create` | `ask` | `posts create`, который создает черновик. |
| `posts.update` | `ask` | `posts update`. Для опубликованного или запланированного поста он проверяет и `posts.publish`. |
| `posts.publish` | `ask` | `posts publish`, сейчас или с `--at-time`. |
| `posts.unpublish` | `ask` | `posts unpublish`. |
| `posts.delete` | `ask` | `posts delete`, который отправляет пост в корзину. |
| `posts.delete.force` | `ask` | `posts delete --allow-delete`, который удаляет навсегда. |
| Любое чтение | `allow` | `sync`, `posts list`, `posts show` и другие команды чтения. |

Запись страницы идет через маршруты страниц, поэтому она проверяет и их ключи: `pages.publish`, когда публикует или
планирует страницу или меняет опубликованную или запланированную страницу; `pages.delete`, когда удаляет страницу, в
корзину или навсегда; и `pages.delete.force` с `--allow-delete`. По умолчанию каждый спрашивает. После «да» на ключ
`posts` то же действие со страницей больше не спрашивается.

## Группа api

`wordpress blog api` достает до каждой операции WordPress и проверяет те же ключи публикации и удаления:

- **Публикации** нужен `<route>.publish`, например `posts.publish` или `pages.publish`. Это изменение, которое ставит
  `status` в `publish` или `future` либо задает `date`, `date_gmt` или `password`, если только тот же вызов не
  ставит `status` в `draft`, `pending` или `private`.
- **Удалению** нужен `<route>.delete`. С `force=true`, то есть при удалении навсегда, нужен еще и
  `<route>.delete.force`. Оба по умолчанию спрашивают.
- **Изменения, как у команд `posts`, тоже проверяют их ключи.** `api posts-create` и `api pages-create` проверяют
  `posts.create`, а `api posts-update` и `api pages-update` проверяют `posts.update`. Поэтому `posts.create` в `deny`
  останавливает черновики на любом пути.
- **Изменения всего сайта спрашивают.** Установка плагина, смена настроек сайта, создание или изменение пользователя
  (с ролью), новый или измененный комментарий, а также изменения шаблонов, частей шаблонов, виджетов, боковых
  колонок, меню и навигации по умолчанию спрашивают: `api.plugins-create`, `api.comments-create` и подобные. Другие
  изменения api, например медиафайлов, меток и рубрик, выполняются без вопроса.
- Создание пароля приложения никогда не предлагается: WordPress отвечает новым паролем открытым текстом.
- Пакетный маршрут WordPress (`batch/v1`) никогда не предлагается: один пакетный вызов выполнил бы изменения других
  маршрутов в обход их ключей.

`wordpress blog api show <operation>` перечисляет ключи, которые проверяет операция.

## Оставьте публикацию за собой

Любой из этих способов оставляет публичное лицо сайта в ваших руках:

- **Без публикации.** `wordpress blog config set permissions.posts.publish deny`. Черновики по-прежнему работают.
  Изменение опубликованного поста тоже отклоняется, потому что оно было бы публичным.
- **Без удаления навсегда.** `wordpress blog config set permissions.posts.delete.force deny`. Посты по-прежнему
  уходят в корзину, откуда их можно вернуть.
- **Только чтение.** `wordpress blog config set permissions.posts readonly` и
  `wordpress blog config set permissions.api readonly`. Любое чтение по-прежнему работает.

## Агенты и MCP

Через MCP у терминала нет никого, кто ответил бы, и сервер не показывает форму, поэтому изменение с уровнем `ask`
выполняется. Со встроенными уровнями агент через MCP может публиковать и удалять навсегда. Так решил владелец: агент
должен доводить порученную работу до конца. `wordpress blog runs list` показывает каждую публикацию 7 дней
(`keep_successful_runs_for_days`).

Если хотите публиковать сами, поставьте `posts.publish` в `deny` до того, как подключите приложение. Или оставьте
уровни и включите подтверждение для инструмента `wordpress_write` в клиенте агента, и клиент будет
спрашивать вас перед каждым изменением.

`mcp serve --permission posts.publish=deny` и `mcp add … --permission …` делают уровень строже для одного этого
сервера. Они никогда не ослабляют профиль. Смотрите [MCP](./mcp.md#publishing-over-mcp).

## Проверки, которые действуют при любых разрешениях

- **`WCWP_READ_ONLY=1`** отклоняет любое изменение в этой оболочке или в приложении, которое задает переменную.
- **Ваша роль в WordPress.** WordPress отклоняет то, что вашему пользователю нельзя, что бы ни говорил профиль.
  Например, участник не может публиковать.
- **Текст из WordPress это данные.** Заголовки, тексты и имена приходят к агенту с пометкой `untrusted`, поэтому
  агент не принимает их за инструкции.
