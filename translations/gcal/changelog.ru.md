Заметные изменения в `@wirecat/gcal-cli`. По одному разделу на версию, новые сверху.

## 0.3.0 — 31.10.2026

### Добавлено

- **`gcal models list` и `gcal models download <model>` скачивают модель, которой пользуется поиск по смыслу.**
  Подсказка поиска называла `gcal models download e5-small`, а такой команды не было. Модель попадает в папку, общую
  для всех инструментов WireCat, поэтому модель, уже скачанная другим инструментом WireCat, используется как есть.
- **`events move <event> --to-calendar <id>` переносит событие, сохраняя его ID, в другой календарь того же
  аккаунта.** Команда отказывает для календаря, в который вы не можете писать, для того же календаря, для события,
  которое Google не переносит (время для работы, отсутствие, место работы, дни рождения), и для повторения без
  `--series`. Через MCP это команда `events move`.
- **`events update --following` и `events delete --following` меняют или удаляют «это и все следующие»
  повторения.** Изменение заканчивает серию прямо перед повторением и начинает с него новую серию с изменением,
  сохраняя участников; удаление только заканчивает серию. Серии, которая заканчивается после заданного числа раз,
  для новой части нужен `--repeat`.
- **`events list changed:<date>` показывает, что изменилось с какой-то даты**, по данным хранилища: у каждого события
  есть `change` (`new`, `moved` или `cancelled`) и `changed_at`, а у перенесённого — где оно `was`.
- **`events list overlapping` показывает встречи, которые пересекаются**, у каждой `overlaps` — остальные события.
  Учитываются только события, которые занимают ваше время: не отменённые, не на весь день, не отклонённые и не
  отмеченные как свободное время.

### Изменено — может сломать скрипты

- **Создание, изменение, перенос и ответы на приглашения по умолчанию выполняются без вопроса.** `events.create`,
  `events.update`, `events.respond` и новый `events.move` — `allow` (было `ask`); скрипту больше не нужен для них
  `--yes`. `events.delete` остаётся `ask`, включая `--following`. Чтобы снова получать вопрос, задайте ключу `ask`,
  например `gcal personal config set permissions.events.create ask`. Ключи `api.calendar.events.*` останавливают
  запись событий, как только вы их зададите; их встроенное `ask` действует только для команд `api`.
- **Изменению серии, чьё новое правило заканчивает её раньше, нужен ещё и `events.delete.series`**, который по
  умолчанию `deny`. Новый `COUNT`, более ранний `UNTIL` или ограничение для серии, у которой его не было, удаляли
  последующие повторения под одним `events.update`.
- **`sync`, в котором не удался какой-то календарь, ничего не выводит в stdout и завершается с `sync.partial`.**
  Сообщение называет каждый неудавшийся календарь и его ошибку, `details.calendars` содержит результат каждого
  календаря (`error` у неудавшихся), а ошибка говорит, что повтор безопасен. Синхронизированные календари сохранены.
  Синхронизация, остановленная лимитом времени или запросов, по-прежнему отвечает `state: "partial"` и завершается
  успешно.
- **`search` отвечает списком: события в `items`, с `page` в режиме курсора, как любой другой список.** Раньше он
  отвечал одним `item` с `hits`, `has_more` и `untrusted` (WC-OUT-4). Скрипт читает `items` вместо `item.hits`, а
  `page.next_cursor` — значение для `--cursor`. Каждое событие называет свои поля `untrusted`, а почему поиск по смыслу
  не выполнялся, указано в `missing`. `query` и `by` убраны; каждое событие по-прежнему сообщает `found_by`.
- **`links review` отвечает своими проверками в `items`, без `accounts: "all"`.** Раньше он отвечал одним `item` со
  списком. Выбор связей по-прежнему хранится для всего хранилища, поэтому выводятся проверки всех аккаунтов.
- **`search --backend server` отклоняет `--newest`.** Google возвращает совпадения в неуказанном порядке, а gcal
  читает только первую страницу каждого календаря, поэтому в ответе «сначала новые» могло не оказаться самого нового
  события. Совпадения выводятся от ранних к поздним, а `found_by` каждого события — `["google"]`, как пишет поиск по
  хранилищу.

### Исправлено

- **`gcal --help` больше не предлагает параметр `--read-only`, которого нет.** Отказаться от всех изменений в запуске
  позволяет `GCAL_READ_ONLY=1`.
- **`events delete` для события, уже удалённого в Google, выполняется успешно и удаляет сохранённую копию.** Google
  отвечает на такое удаление кодом 410, а когда перестаёт показывать событие — 404; gcal завершался ошибкой в обоих
  случаях и держал событие в хранилище до следующей синхронизации.
- **Ежедневная полная синхронизация больше не помечает удалёнными события вне своего окна.** Более ранние и более
  поздние одиночные события, перенесённые повторения и закончившиеся серии помечались удалёнными, а их события —
  отменёнными. Хранилище, повреждённое так, восстанавливается при следующей синхронизации.
- **Повторяющееся событие, перенесённое на другое время, больше не сохраняет повторения в старое время** после
  инкрементальной синхронизации.
- **`sync --rescan`, остановленный лимитом, больше не оставляет недостигнутые календари на инкрементальных раундах.**
- **Создание, которое Google выполнил, а хранилище не смогло сохранить, называет ID события**, поэтому повтор с `--id`
  его находит.
- **`sync` пишет в хранилище гораздо меньшим числом транзакций, а ежедневный полный раунд запрашивает повторения
  только у изменившихся серий.** `events list` по времени и `people list` читают хранилище быстрее.
- **Отказ Google для отсутствующего или запрещённого объекта называет причину**: `google.not-found` или
  `google.denied`, так что скрипт может ветвиться по ней, а не по сообщению.
- **Вход, прерванный тайм-аутом или Ctrl-C, всё равно закрывает открытое им хранилище.**
- **`gcal api call --help` больше не показывает `Default: [object Object]` для `--params`.** Если параметр не указан,
  параметры по-прежнему не отправляются.
- **`gcal` запускается примерно вдвое быстрее** (`gcal --help`: было 0,40 с, стало 0,19 с, на ноутбуке с Node 24).
  Пакет поставляет одну собранную программу вместо сотен модулей. Синхронизация также быстрее обрабатывает каждое
  событие.

### Безопасность

- **`search --backend server` помечает как написанные другими правильные поля.** Его список `untrusted` называл
  `title` и `location`, а ответ держал их в `hits`, поэтому агент, следующий списку, не считал их данными. Теперь
  каждое событие само называет `title` и `location`.
- **`gcal api` отклоняет пустой ID, `.` или `..` в адресе запроса** (`api.bad-path-id`). Такой ID направлял адрес на
  другой метод Google, `calendars/primary/events/..` — на сам календарь; теперь ничего не отправляется.
- **`session end` в запуске с перенесёнными папками сохраняет вход владельца в системном хранилище ключей и говорит
  об этом.** Запуск с `GCAL_CONFIG_DIR`, `GCAL_STATE_DIR` или перенесённым `HOME` использует запись хранилища ключей,
  общую для всех запусков gcal; завершение сеанса там вывело бы владельца из аккаунта везде. Теперь он отвечает
  `kept: "keyring"` и говорит, что запуск по-прежнему выполнил вход; `ended` равно `true` только тогда, когда у запуска
  был собственный вход для удаления. Запуск в обычных папках завершает вход, как раньше.
- **Вход в запуске с перенесёнными папками больше не заменяет вход владельца в системном хранилище ключей.** Он
  попадает в собственную запись запуска, `gcal-cli:<config folder>`, которую запуск читает первой и которую удаляет его
  `session end`; в остальном запуск читает запись владельца и никогда её не меняет. Поэтому тестовый вход с другим
  аккаунтом Google больше не может переключить профиль владельца.

## 0.2.0 — 30.10.2026

### Добавлено

- **Навык `gcal-cli` публикуется в ClawHub как `wirecat-gcal` после каждого выпуска и сообщает OpenClaw, что ему
  нужен `gcal` и как его установить** (`metadata.openclaw`: `requires.bins` и npm-пакет `@wirecat/gcal-cli`). Если
  `gcal` нет в PATH, OpenClaw помечает навык как неготовый и предлагает установить пакет. Claude Code и Codex этот
  блок игнорируют.

## 0.1.1 — 29.10.2026

### Исправлено

- **Заголовок руководства для агента (`skills/gcal-cli/SKILL.md`) снова корректный YAML.** Его `description`
  содержал `Calendar: sync`, что парсер YAML читает как вложенное отображение, поэтому строгие загрузчики навыков и
  индекс навыков на сайте WireCat отклоняли файл. Текст не изменился, кроме тире вместо этого двоеточия.

## 0.1.0 — 29.10.2026

### Добавлено

- **`gcal <profile> session start | status | end` входит в Google через браузер с доступом к Календарю только на
  чтение.** Пока используется ваш собственный клиент Google OAuth (`--client-file` или `GCAL_GOOGLE_CLIENT_ID` и
  `GCAL_GOOGLE_CLIENT_SECRET`); как его создать, описано в [настройках](./configuration.md#your-own-google-client).
  Вход хранится в системном хранилище ключей или, с `--credential-storage file`, в личном файле (права 600) там, где
  хранилище ключей не работает. `session status --check` спрашивает у Google, действует ли вход. `--grant write`
  дополнительно запрашивает `calendar.events`, нужный для записи событий, а `--grant sharing` — `calendar.acls`,
  нужный для управления доступом. `gcal session list` выводит профили на этом компьютере, у каждого `signed_in`,
  `account` и `credential_storage`; ни одна команда не выбирает профиль за вас.
- **`gcal <profile> sync` копирует ваши календари в локальное хранилище WireCat, и команды чтения работают без
  сети.** `calendars list | sync | unsync`, `events list | show`, `search`, `people list | link` и
  `links review | resolve` — общие календарные команды WireCat, поэтому другие инструменты WireCat видят те же
  события и тех же людей. Первая синхронизация читает ваши собственные календари от года назад до трёх месяцев
  вперёд; каждая следующая просит у Google только изменения. Повторения повторяющегося события сохраняются по
  отдельности, включая отменённые. `sync --embed` дополнительно индексирует события для поиска по смыслу. Каждый
  ответ перечисляет в `untrusted` поля, которые написал отправитель приглашения, чтобы агент читал их как данные.
- **Большая синхронизация продолжается за несколько запусков.** `sync` сама останавливается до истечения лимита
  времени (15 минут в терминале, 45 секунд через MCP; `--timeout` его меняет, `--max-pages <n>` дополнительно
  уменьшает число запросов к Google) и сохраняет результат после каждой страницы. Частичный ответ содержит
  `state: "partial"`, сколько уже сделано, и команду для следующего запуска. `--rescan` начинает все календари
  заново. `gcal <profile> status` показывает ход синхронизации каждого календаря, `partial` или `complete`, и сколько
  времени прошло с последнего продвижения.
- **`gcal <profile> calendars busy` показывает, когда календари и люди заняты**, по ответу Google о
  занятости, который говорит когда, но никогда — чем. `--duration-minutes` выводит промежутки, свободные у всех, в
  пределах `--hours` (по умолчанию 09:00-17:00), с понедельника по пятницу; те, кого Google не показывает,
  перечислены в `unknown`. Ничего не сохраняется.
- **`gcal <profile> search --backend server <words>` использует собственный поиск Google Календаря** по
  синхронизируемым календарям. Он только читает, ничего не сохраняет и находит события и за пределами
  синхронизированного периода. По умолчанию используется `--backend archive`, локальное хранилище.
- **`gcal <profile> events create | update | delete | respond` меняют Google Календарь после
  `session start --grant write`.** Без этого права запись завершается с `permission_error` и называет нужный флаг.
  Изменение отправляет синхронизированную версию, поэтому событие, изменённое в Google с тех пор, даёт
  `event.conflict` и никогда не перезаписывается. Создание, ответ на которое потерялся, заканчивается
  `outcome_unknown` с ID; при повторе с этим ID событие находится. `events create --repeat <rule>` создаёт
  повторяющееся событие, а `events update --series --repeat <rule>` меняет его правило. Новые даты делают событие со
  временем событием на весь день, а новое время делает событие на весь день событием со временем, сохраняя ссылку
  Meet и файлы Drive. `respond` меняет только ваш собственный ответ. Запись доступна и как инструменты MCP, с теми же
  параметрами, что в командной строке.
- **`gcal api list | show | call` и отдельная команда `gcal <profile> api <method>` для каждого метода дают доступ ко
  всем методам Google Calendar API v3**, которые gcal может обслужить. Они созданы из описания API от Google, и
  каждый ответ сверяется с ним. Уведомления Google об изменениях (`watch`, `channels.stop`) не предлагаются: им
  нужен публичный веб-адрес.
- **У каждой команды и каждого метода Google Календаря есть ключ разрешения**, например `events.create` или
  `api.calendar.events.insert`. Изменение сначала спрашивает (`--yes` в скрипте), в том числе открытие доступа к
  календарю и передача его другому аккаунту; через MCP отвечать некому, поэтому `ask` позволяет агенту выполнить
  его. Три ключа стоят в `deny`, пока вы их не разрешите: `events.notify` (Google рассылает письма участникам),
  `events.delete.series` (удаление всех повторений повторяющегося события) и `sharing.notify` (Google отправляет
  письмо человеку, которому открыт календарь). Команды `api` проверяют те же ключи, что и запись событий, а запись
  события проверяет ещё и ключ своего метода Google, поэтому `permissions.api readonly` останавливает и то и другое.
  Очистка календаря (`calendars.clear`) запрещена и никогда не предлагается через MCP, как и `api call`.
  `--dry-run` выводит все ключи, которые проверяет вызов, с их уровнями. Ключ, не называющий ни одного метода,
  отклоняется, а `gcal doctor` показывает такие ключи, сохранённые в файле.
- **Код доступа, PIN и пароль встречи никогда не покидают Google.** Они никогда не сохраняются: ссылка для
  подключения хранится без строки запроса, а строка описания или места события, где упоминается код доступа,
  пароль или PIN, отбрасывается. Команды `api` тоже удаляют их из каждого ответа с событием, в терминале и через
  MCP.
- **`gcal <profile> mcp serve` предоставляет команды профиля агенту**, а `mcp add claude-code | codex`,
  `mcp config`, `mcp check`, `mcp revoke` и `mcp server start | stop | status` настраивают это.
  `--profiles <names|all>` обслуживает несколько профилей; профиль никогда не выбирается сам, поэтому
  `gcal mcp serve` без профиля выводит их список и останавливается. Сервер сообщает агенту, какой текст написали
  другие люди, а управляющие символы в ответе показываются явно, поэтому текст приглашения ничего не может скрыть от
  агента.
- **`gcal --help` показывает, что умеет gcal и с чего начать, а `gcal guide` даёт пошаговые сценарии**: настройка,
  доступ для агента, поиск времени. `gcal skill install` добавляет навык инструмента для Claude Code, Codex,
  Gemini CLI, OpenClaw и Hermes Agent.
- **`gcal doctor` показывает, что настроено, без сети и без хранилища ключей**: версию, пути, хранилище, клиент OAuth,
  блокировку профиля и файлы входа.
- **`gcal <profile> runs list | show` показывает сохранённые запуски gcal**, включая вход и выход: успешные — 7
  дней, неудачные — 30. Секреты скрыты; `config set record_input false` не сохраняет ни одного введённого вами
  слова.
