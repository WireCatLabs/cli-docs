Используйте эту страницу, прежде чем позволить ИИ-агенту, скрипту или другому человеку работать с вашим аккаунтом Telegram через `tg`. Он показывает, как для каждого профиля решить, что можно только читать, что вас спрашивают в первую очередь, а что можно продолжать без вопросов. Вы сможете сделать профиль доступным только для чтения, разрешить одно действие, например отправку, и узнать, какие другие проверки все еще применяются.

Слова, которые используются на этой странице:

- **Профиль**: именованный набор настроек для одного аккаунта или бота, например `work` ([профили и боты](./profiles.md)).
- **Ключ разрешения**: имя команды или группы команд, например `messages` или `messages.send`. Более длинный ключ более конкретен.
- **Уровень доступа**: что происходит при выполнении этой команды: `deny`, `readonly`, `ask` или `allow`.

Начните с чтения и разрешайте изменения только тогда, когда они вам нужны.

## Выберите уровень доступа

| Уровень | Поведение |
|---|---|
| `deny` | Действие запрещено, включая чтение. |
| `readonly` | Чтение разрешено; изменения запрещены. |
| `ask` | Перед изменением запрашивается подтверждение в терминале. |
| `allow` | Действие может выполняться без дополнительного вопроса. |

Отказ означает, что нужно проверить запрошенное действие и настройки. Он не означает, что подключение
аккаунта нарушено. Не просите агента снять ограничение только ради завершения задачи.

## Разрешите одно действие

```sh
tg work config set permissions.messages.send ask
```

Замените `work` именем вашего профиля. Чтобы по умолчанию разрешать чтение сообщений и запрещать изменения:

```sh
tg work config set permissions.messages readonly
```

Более конкретные ключи имеют приоритет: `permissions.messages.send ask` по-прежнему разрешает отправку с вопросом
в терминале, а через MCP — без формы подтверждения на сервере. Установите для этого ключа `readonly`, чтобы запретить отправку.
Проверьте остальные исключения с помощью `config show`.

Это контролирует сообщения. Другие действия, такие как реакции или администрирование чата, имеют свои собственные ключи разрешения. Полный профиль, доступный только для чтения, и все ключи находятся в [что может делать профиль](./configuration-reference.md#what-a-profile-may-do).

## Разрешения для бота

Разрешения и ограничения бота относятся к разделу бота. Чтобы запрашивать подтверждение в терминале перед отправкой:

```sh
tg support config set permissions.bot.messages.send ask --bot
tg support config set sends_per_hour 30 --bot
```

## Ограничьте получателей и повторные отправки

Список получателей ограничивает чаты, в которые профиль может отправлять сообщения. Почасовой лимит отправки помогает остановить цикл. Эти проверки остаются активными, когда разрешена конкретная команда. Команды для управления ими находятся в [защите отправки](./security.md#the-send-guard).

## Временное изменение для сервера MCP

Добавьте `--permission messages.send=deny` в команду запуска сервера, чтобы запретить отправку для этого
процесса. Сохранённые настройки не меняются. Параметр только ужесточает: переопределение, которое ослабило бы уровень профиля, отклоняется при запуске. Через MCP значение `ask` не требует формы подтверждения на сервере: приложение управляет
своими подтверждениями и может разрешить вызов без повторного вопроса. Используйте `deny` или `readonly`, чтобы запретить изменения. [Настройка в браузере](./remote.md) объясняет подключение целиком.

## Разрешить агенту менять собственные ограничения

MCP сохраняет в списке команды, меняющие возможности следующего запуска, но по умолчанию помечает их недоступными: `config set|unset`, списки
получателей, правила чатов и ответов, согласия, расписания, `server install`, `skill install`, ключи моделей,
таймеры архива вложений и `flood clear`. Их открывает один ключ:

```sh
tg work config set permissions.mcp.authority allow
```

Для сервера бота добавьте `--bot`: `tg support config set permissions.mcp.authority allow --bot`.
По умолчанию действует `deny`; `allow` и `ask` разрешают выполнение команд. Оставляйте `deny` у профиля,
который даёте агенту: иначе он сможет ослабить собственные ограничения. Агент не может поменять этот
ключ через `config set`, потому что ключ закрывает и эту команду. См. [MCP-сервер](./mcp.md#commands-that-change-what-a-later-run-may-do).

## Прямые вызовы Bot API

Вызовы `bot api <operation>` обходят защиту отправки и список получателей бота. MCP показывает их как недоступные,
пока `permissions.bot.api` не равен `allow` или `ask`. По умолчанию это `deny`; более общее
`permissions.bot: allow` их не включает. Выдайте отдельное разрешение из терминала:

```sh
tg support config set --bot permissions.bot.api allow
```

Верните `deny`, чтобы снова запретить выполнение этих инструментов; они останутся в списке. Агент не может менять этот ключ через MCP.

## Ограничения и подробные правила

Агент, который может редактировать файлы конфигурации или выполнять неограниченные команды терминала, может изменить эти настройки. Прочтите [безопасность](./security.md), прежде чем предоставлять этот доступ. Информацию о вложенных разрешениях и точных ключах команд см. в разделе [что может делать профиль](./configuration-reference.md#what-a-profile-may-do).

## Сохранение черновика

`messages send --draft` использует отдельное разрешение `drafts`. Сохранение меняет черновик Telegram для чата или темы, не отправляет сообщение и не записывает текст черновика в журнал. `deny` или `readonly` запрещает сохранение; `ask` запрашивает подтверждение в CLI, а в MCP действует порядок одобрения приложения-клиента.

В MCP команда `messages send` также должна быть разрешена на уровне команды. Настройка `drafts: allow` не отменяет `messages.send: deny` или `readonly`.
