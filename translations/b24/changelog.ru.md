Заметные изменения в `@wirecat/bitrix24-cli`. По одному разделу на версию, новые сверху.

## 0.28.0 — 25.11.2026

### Добавлено

- **`search all` находит сделки и лиды по смыслу их дел:** звонков, писем, комментариев и задач, другими словами или
  на другом языке, и показывает в результате отрывок дела. `b24 work sync --embed` строит индекс уже скачанной моделью
  (`b24 models download embeddinggemma`); пока ее нет, `search all` сообщает, что искал только по словам. Нужна
  включенная настройка `activities` (`@wirecat/cli-core` 0.751.0).
- **`sync --embed` и `search all` по смыслу** (cli-core 0.751.0). С включенной настройкой `activities` команда
  `sync --embed` индексирует скопированные комментарии таймлайна, письма, звонки, встречи и задачи уже скачанной
  моделью, и тогда `search all` находит сделки и лиды по тому, что значат их дела, на русском или любом другом языке,
  а не только по словам. Навык говорит агенту искать по смыслу, прежде чем читать каждое дело; подробности в
  `b24 skill show reading`.

### Изменено — может сломать вызовы

- **`synced[].saved` в ответе `sync` считает только изменившиеся строки** (новые, другие, удаленные или вернувшиеся),
  поэтому синхронизация без нового отвечает 0.
- **b24 построен на cli-core 1.0 и cli-base 1.0.** После первого запуска хранилище переходит на версию 74, и
  открывают его только инструменты на cli-core 1.0, поэтому обновляйте все CLI WireCat на этом компьютере вместе.
  Миграция сохраняет копию для отката и не запускается, если не может ее записать (`store migrate --no-backup`
  мигрирует все равно).
- **`sync --rescan` больше не дает синхронизации отметить удаленной большую часть записей одного вида.** Он только
  заново перечисляет все. Когда защита придерживает проход, `sync --allow-deletions <count>` разрешает отметить
  удаленными не больше этого числа записей. Этот флаг для владельца в терминале, сервер MCP его не предлагает.
- **MCP больше не предлагает `schedule exec`.** Это собственная команда таймера, и она запускает только файл
  расписания из папки расписаний b24. Агент запускает сохраненное расписание командой `schedule run <name>`. См.
  [Безопасность](./security.md#timers).
- **Вызов MCP, который называет запрещенную папку, отвечает `permission_error`**, а не `validation_error`.

### Исправлено

- `search all` показывает после совпавшего имени имя, которое отличается от него одной буквой, и находит латинское
  имя, набранное кириллицей, и русское имя, набранное латиницей, с пометкой `match: corrected`.

## 0.27.0 — 24.11.2026

### Добавлено

- **Файлы клиентов: `files list`, `files download` и `files sync`.** `files list --deal 12` (или `--lead`, `--person`,
  `--organization`) читает с портала файлы одной записи: файлы в ее файловых полях, документы, созданные по
  шаблонам (PDF, если портал его сделал, иначе файл Word), и файлы Диска, прикрепленные к ее делам и комментариям
  в таймлайне. `files download <id>` сохраняет файл в папке состояния и читает его текст, который потом находит
  `search all`. Источник, который вебхуку читать нельзя, например файлы дел без области `disk`, назван в `issues`, а
  остальные все равно показываются. Каждое скачивание запрашивает у портала новую ссылку и скачивает файл только с
  портала; ни одна ссылка не попадает в хранилище или в ответ. `files: deny` действует и на `api call` методов, через
  которые читают эти команды. См. [Файлы клиентов](./usage.md#client-files).

### Изменено — может сломать вызовы

- **`api call` скрывает больше ссылок.** Теперь он использует правило cli-core: кроме ключей скачивания и путей
  портала с токеном, любая ссылка с `auth=`, `access_token=`, `api_token=` или `X-Amz-Signature=` печатается как
  `[link removed]`, на каком бы адресе она ни была. `ERROR_NOT_FOUND` Диска (например, `api call disk.file.get`
  несуществующего файла) теперь `not_found`, код выхода 6, а не `validation_error`.
- **`search all` может вернуть новый вид результата, `crm_file`**, текст скачанного файла. Скрипт, который ветвится
  по `kind`, его получит. Он приходит с `@wirecat/cli-core` 0.710.0, хранилище которого переходит на версию 69 (только
  вперед).
- **`account remove --delete-data` отказывает с `account-remove.account-shared`, деталь `account`.** Было
  `account-remove.portal-shared` с деталью `portal`. Теперь это общая CRM-команда cli-core (`@wirecat/cli-core`
  0.722.0). Она по-прежнему отказывает, пока другой профиль на этом компьютере читает тот же портал, даже если его
  сеанс завершен. С `--dry-run` она теперь предупреждает и показывает, что будет удалено, а раньше завершалась
  ошибкой.
- **`account remove --delete-data` отказывает, когда b24 не может понять, какой портал у другого профиля**
  (`account-remove.account-unknown`, деталь `profile`): у профиля сохраненный вебхук не читается, а `session start`
  его никогда не запоминал. `--keep-data` по-прежнему удаляет.
- **`session start` отказывает во втором входе на тот же портал тем же пользователем общим текстом cli-core.** Причина
  остается `session.duplicate`; ее деталь `portal` теперь `account`, а сообщение говорит завершить другой профиль
  командой `b24 <profile> session end`. Вход по вебхуку в профиль с именем `files` или `foreign-contacts`, папки,
  общие для всех порталов, отклоняется с `profile.reserved`.
- **MCP-сервер больше не предлагает `schedule exec`, и тот запускает только файл расписания из собственной папки
  расписаний b24** (`@wirecat/cli-core` 0.739.0). Символическая ссылка или `..`, ведущие в другое место, отклоняются с
  `schedule.outside-folder`. Установленные таймеры продолжают работать. Агент запускает сохраненное расписание
  командой `schedule run <name>`.

### Исправлено

- **Сделка, которая переходит в стадию в ту же секунду, когда были заданы ее правила `stage-tasks`, теперь открывает
  свою задачу** (`@wirecat/cli-core` 0.739.0). История стадий портала хранит целые секунды, поэтому такой переход
  читался как сделанный до правил и не открывал задачу.

## 0.26.0 — 18.11.2026

### Изменено — может сломать вызовы

- **Запись в MCP Registry спрашивает, какие профили обслуживать.** Она запускала `mcp serve --profiles all`, поэтому
  клиент, который установил сервер из реестра, получал доступ ко всем аккаунтам на компьютере без выбора владельца.
  Теперь `--profiles` — обязательный аргумент с примером `personal`: клиент спрашивает один профиль, список через
  запятую или `all`. Почему: CLI никогда не выбирает аккаунт за владельца
  ([WC-MCP-9](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/mcp.md#wc-mcp-9--a-server-serves-the-profiles-it-is-told-with-one-connection-for-each)). Обратите внимание: клиент, настроенный по старой записи, сохраняет `--profiles all`, пока его не настроят заново;
  сервер, добавленный вручную или через `mcp config`, не меняется.

### Исправлено

- **Записи, которые хранит ваш провайдер телефонии.** Портал, который работает с внешним провайдером телефонии,
  например с облачной АТС Билайна, ссылается на каждую запись на сервере провайдера. b24 отклонял такую ссылку, и
  `meetings transcribe` не превращал в текст ни один из этих звонков. Теперь он переходит по ссылке по https на адрес
  в публичном интернете, никогда на этот компьютер или в локальную сеть, и не отправляет с ней ничего из вашего входа
  в Битрикс24. См. [Звонки](./calls.md#recordings).
- **`meetings transcribe --max-meetings` считает звонки с записью.** Звонок без записи на портале по-прежнему
  попадает в `failed`, но больше не расходует лимит. Раньше, когда у самых новых звонков не было записи,
  `--max-meetings 1` ничего не превращал в текст.
- **Запись, присланная без типа аудио.** Сервер провайдера телефонии, например облачной АТС Билайна, присылает запись
  как `application/octet-stream` и называет файл, `call.mp3`, в `Content-Disposition`. b24 отклонял ее как не аудио
  (`recording.not-audio`), поэтому `meetings transcribe` не превращал в текст ни один из этих звонков. Теперь формат
  берется из имени файла, если тип его не называет.

## 0.25.0 — 17.11.2026

### Изменено — может сломать вызовы

- **`meetings transcribe` отдает тот же отчет, что и beeline.** Длительность аудио теперь `audio_ms`, в миллисекундах
  (было `audio_seconds`). У каждого звонка с ошибкой есть `ref`. Звонок без записи на портале попадает в `failed` с
  причиной `recording.missing`, а `without_recording` больше нет. Раньше b24 и beeline отдавали один и тот же отчет в
  двух видах, и скрипт, написанный для одного, не мог прочитать другой.

### Исправлено

- **Вход через локальное приложение, сохраненный прежней версией b24, работает и после обновления.** Прежние версии
  хранили портал в сохраненном входе под другим именем, и новое хранилище входа отвечало "the saved sign-in cannot be
  read; sign in again".

## 0.24.0 — 17.11.2026

### Добавлено

- **Основан на cli-core 0.683.0** (было 0.670.0), с его дополнениями для CRM. `deals list` и `leads list` принимают
  `updated:`, `created:`, `closed:` и `owner:` (`owner:me` это ваш собственный пользователь портала).
  `pipelines show --since-time --until-time` показывает воронку за период с закрытыми сделками, длительностью цикла,
  ответственными и причинами проигрыша. `deals show` отвечает `stage_history` по собственной истории стадий портала.
  `stages list` отвечает `stage_task`. См.
  [историю изменений cli-core](https://github.com/WireCatLabs/cli-core/blob/main/CHANGELOG.md).
- **`people create` и `organizations create` принимают `--email` и `--phone`.** Телефон принимается только в
  международном виде (`+…`). `people update` и `organizations update` по-прежнему их отклоняют: Битрикс24 добавил бы
  новые к старым, а не заменил бы их.
- **`calls export` записывает звонки других телефонных систем в контакт клиента в Битрикс24**, каждый один раз, через
  `telephony.externalCall.register` и `finish`. По умолчанию выключено. Нужны настройка `export_calls`, права на оба
  метода и вход через локальное приложение, потому что Битрикс24 не дает ни одному вебхуку записать звонок.
  `--dry-run` показывает поля каждого звонка и куда он попадет, и ничего не отправляет. См. [Звонки](./calls.md).
- **Звонки телефонии Битрикс24 в хранилище.** `meetings sync` копирует историю звонков портала. Каждый звонок
  становится встречей вида «звонок» с направлением, номером клиента, сотрудником, временем разговора и тем, чем он
  закончился. Копируются звонки пользователя, который вошел, или пользователей, выбранных в `unassigned`, но никогда
  не всего портала. Сотрудник в копии это пользователь портала. Клиент связывается с контактом, аккаунтом в
  мессенджере или звонками другой телефонной системы с тем же мобильным номером. `meetings list`, `show`,
  `transcript`, `export` и `people` их читают, а `memo context` показывает их в истории человека. Вебхуку нужна
  область `telephony`. См. [Звонки](./calls.md).
- **`meetings transcribe` и `models`** превращают записи звонков в текст локальной моделью распознавания речи на этом
  компьютере.
- **`download_recordings`** сохраняет запись каждого звонка в папке состояния, чтобы WireCat Desktop мог ее
  воспроизвести. **`phone_region`** читает номера, которые портал пишет без `+`.
- **`b24 setup` проводит вас через подключение портала**, и WireCat Desktop показывает те же шаги: создать входящий
  вебхук, отметить его права, вставить его адрес. `b24 setup show --json` выводит шаги (формат настройки v1).
  `b24 work setup apply` проверяет адрес на портале так же, как `session start`, и только после этого сохраняет его.
  Локальное приложение по-прежнему подключается одной командой `session start --portal … --client-id …`, она
  показана в конце.
- **Права, которые нужно отметить, теперь называют `task` для задач Битрикс24, `telephony` для звонков, а также
  `disk` и `documentgenerator` для файлов и документов клиентов**, рядом с `crm`, `user_basic` и `department`. Если
  отметить `disk` сейчас, не придется снова менять вебхук, когда появится работа с файлами.
- **`changes list`** из cli-core 0.678.0: что изменилось в копии CRM за период, и `--format report` для утренней
  сводки.
- **`sync` тоже копирует звонки портала**, после CRM, как `meetings sync`, поэтому синхронизация WireCat Desktop и
  синхронизация после установки приносят звонки. Шаг звонков, который не удался, например из-за вебхука без области
  telephony, становится заметкой, а синхронизация CRM все равно проходит. Настройка `sync_calls` (включена, если не
  задана) исключает звонки. Если пришли звонки, а `phone_region` не задан, заметка говорит, как его задать. См.
  [Звонки](./calls.md).

### Изменено — может сломать вызовы

- **`sync` каждый раз читает историю стадий портала**, в первый раз на 90 дней назад, поэтому воронка и `deals show`
  учитывают стадии, которые сделка действительно прошла. Вебхук без права на `crm.stagehistory.list` называет это в
  проблемах синхронизации.
- **Чтение CRM без сети берет вашего пользователя портала из сохраненного входа**: из `B24_TOKEN`, связки ключей
  системы или файла с учетными данными, без сети. Если связка ключей недоступна, чтение предупреждает и берет файл.
  Если вход не найден, сделки и лиды не показываются.
- **`pipelines list`, `stages list` и `pipelines show` не показывают стадию, которую портал удалил**, если в ней нет
  сделки.
- **Навык агента стал короче.** `SKILL.md` держит то, что агенту нужно на каждом ходе (правило профиля, ответы из CRM,
  границы записи, `ask` в MCP, который не спрашивает, вывод), примерно в 8 КБ вместо 18 КБ, а остальное дает ссылками
  в `skills/bitrix24-cli/references/`: чтение, запись, MCP, вывод и настройка. Ни одно правило не убрано. Навык
  теперь говорит, что изменилось с тех пор, как его написали. Дела, задачи и комментарии к сделкам читаются, когда
  владелец их включит. `deals list` принимает `updated:`, `created:`, `closed:` и `owner:me`. `pipelines show`
  считает воронку за период. `people create` и `organizations create` принимают `--email` и `--phone`, а `update` их
  отклоняет. Профиль, который не администратор, без сети читает только свои сделки и лиды. Агент, который читает
  навык, тратит примерно на 2 500 токенов меньше на каждом ходе.
- **`people`, `organizations` и `users` теперь общие команды CRM WireCat**, с теми же словами, запросом и ответом,
  что во всех инструментах CRM. Компания отвечает `type` и `own` вместо `type_id`. Ее отрасль, выручка и валюта
  переехали в `provider_metadata`, а `industry_id:` больше не фильтр. Каждый список и показ с портала отдает
  пользовательские поля в `provider_metadata`, каждая запись называет свои поля `untrusted`, а `--offline`
  по-прежнему их отклоняет. Пользователь это сущность `crm_user`, а не `user`. Имя, под которое подходят несколько
  записей, дает `crm.record-ambiguous`, а не `organization.ambiguous` или `person.ambiguous`.
- **Эти три списка листаются через `--limit` (от 1 до 250, по умолчанию 50) и `--page`.** `--all`, лимит больше 250
  и `defaults.limit` профиля к ним больше не применяются. `users list name:` ищет часть полного имени среди всех
  сотрудников, а не собственным поиском портала по имени.
- **`people create`, `people update`, `organizations create` и `organizations update` теперь общие записи.** Они
  принимают `--name`, `--owner`, `--field`, а для людей `--first-name`, `--last-name` и `--position`. `--body`
  убран (любое другое поле записывает `api call`). Каждая отвечает записью в том виде, в каком ее держит портал, и
  сохраняет ее.
- **Подписи в `--field` нужен сначала `sync`.** До него называйте поле его кодом, как его выводит `fields list`.
- **Счетчик 100 чужих контактов и компаний в день теперь в cli-core** и начинается заново с нуля. Его сообщение и
  причина (`crm.foreign-contacts-spent`) общие, а `api call` отклоняет чтение клиентов с
  `crm.client-reads-admin-only`.
- **После обновления войдите снова, если входите через локальное приложение (`session start --app`).** Сохраненный
  вход перешел на форму cli-core, старый больше не читается. Вход через вебхук это не затрагивает.
- **Запуск с перенесенными папками (`B24_CONFIG_DIR`, `B24_STATE_DIR`) больше не обновляет истекший вход через
  приложение.** Битрикс24 заменяет токен обновления при каждом обновлении, поэтому такой запуск вывел бы из входа
  собственные запуски владельца. Он сообщает об этом. Обновите вход в запуске без перенесенных папок.

### Исправлено

- **Контакт, переданный коллеге, уходит из копии при следующем `sync`**, вместе с телефоном и e-mail. Раньше его
  единственные телефон и e-mail оставались до `sync --rescan`.
- **Поле, которое портал не описывает, все равно видно**, из `userfield.list`, без подписи: `sync` его сохраняет, а
  `--field` может его задать.
- **`api call` отклоняет чтение лидов всем, кроме администратора Битрикс24**, как уже отклоняет чтение контактов и
  компаний. Лид хранит собственные имя, телефоны и e-mail, поэтому `crm.lead.list` отдавал сотруднику контактные
  данные лидов всего портала в обход правила 100 в день.
- **Стадии успеха и провала, прочитанные из `EXTRA.SEMANTICS`, теперь успех и провал, а не открытые.** У стадии,
  которую портал перечисляет без короткого `SEMANTICS`, есть только `success`, `failure` или `apology`, а `sync`
  сохранял ее как открытую. Их сделки считались открытыми, а `deals close` не находил стадию успеха.
- **Круг чтения дел, растянутый на несколько запусков `sync`, больше не теряет то, что изменилось за это время.** Круг
  заканчивался временем последнего запуска, поэтому `since` следующего круга пропускал каждое дело, задачу и
  комментарий, измененные в промежутке. Задача, завершенная в это время, оставалась открытой в копии, пока снова не
  менялась. Теперь круг заканчивается временем своей первой страницы.

### Безопасность

- **Профиль, который не администратор портала, без сети читает только назначенные ему сделки и лиды.** Копия
  хранится одна на портал, поэтому профиль обычного сотрудника на том же портале, что и профиль администратора, читал
  каждую сделку, которую синхронизировал администратор, а `search all` находил их по e-mail и телефонам контактов.
  Теперь чужая сделка дает `not_found`, а отчеты считают только свои. Профиль, чей вход не называет пользователя
  портала, не читает ни одной сделки копии, сообщает об этом и завершается с кодом 1. Войдите снова через
  `session start`. Администратор, как его определил последний `sync`, читает всю копию, как раньше. Пока не прошел
  `sync` этой версии, каждый профиль читает только свои сделки и лиды: выполните `sync` один раз после обновления.
- **Ни одной ссылки на скачивание файла в копии или в выводе.** Файл в пользовательском поле записи CRM теперь
  хранится как id файла, в `sync` и в каждом ответе `show`, `list` и записи: ссылка Битрикс24 на скачивание
  (`urlMachine`, `downloadUrl`) несет токен доступа. Файл без id и ссылка на портал с токеном показываются как
  `[link removed]`. Сайт или поле-ссылка, введенные вручную, остаются. `api call` выводит `[link removed]` вместо
  каждой ссылки на скачивание, каждого `publicUrl` созданного документа и каждой ссылки на портал с токеном. Копия,
  синхронизированная до этой версии, может еще хранить такие ссылки. `b24 work sync --rescan` перезаписывает записи,
  которые портал все еще перечисляет. Запись, удаленная или вне охвата синхронизации, хранит то, что хранила, до
  `account remove --delete-data`. См. [безопасность](./security.md).
- **`api call` отклоняет методы, которые создают публичную ссылку**: `enablePublicUrl` созданных документов,
  `crm.invoice.getExternalLink` и `salescenter.payment.getPublicUrl`, и чтение, и запись, как уже отклонял
  `disk.*.getExternalLink`.
- **Скачивание записи звонка попадает в журнал без кода вебхука**: запись запуска хранит `/rest/:user/:token/…`, а
  не ссылку.

- **Навык агента покрывает то, что агенту нужно.** В `b24 skill show` теперь есть коды выхода и причины ошибок, MCP
  и ловушка с `ask`, первая настройка от вебхука до первой синхронизации, границы записи и подводные камни.
- В примерах везде профиль `work` вместо `personal`.
- **`b24 commands` показывает CRM по разделам.** Сделки, лиды, контакты и компании разделены на Read и Write,

- **Ежедневный `sync` больше не читает всех клиентов заново.** Раунд изменений читал каждый контакт и каждую

## 0.5.0 — 07.11.2026

### Добавлено

- `sync` копирует воронки, компании, контакты, сделки и лиды портала в локальное хранилище WireCat: то, что
  изменилось с прошлой синхронизации, или все с `--rescan`; раз в день он также находит, что портал удалил.
  `store status` показывает, насколько продвинулся каждый вид. Синхронизация останавливается до своего срока или
  `--max-pages`, а следующая продолжает с этого места.
- `deals close <ref> won|lost` и `leads close`, на первую стадию успеха или провала воронки записи, а также
  `deals delete` и `leads delete`, которые сначала спрашивают.
- `deals create` и `update` принимают `--pipeline`, `--stage`, `--amount` с `--currency`, `--close-date` и
  `--owner`; лиды принимают то же, кроме `--close-date`. Стадия проверяет ключ перемещения, а стадия успеха или
  провала — еще и ключ закрытия.
- `search all` находит сохраненные сделки и лиды рядом с сообщениями, заметками и событиями других инструментов
  WireCat. При `deals.list: deny` он не берет сделки и называет их в `missing` и в stderr, и так же для лидов; если
  запрещены все виды, о которых его спросили, он отклоняется (`search.all-denied`).
- `b24 --help` и `b24` без аргументов начинаются с того, для чего нужен `b24`, что попробовать первым и с чего начать.

### Изменено — может сломать вызовы

- `deals`, `leads`, `pipelines` и `stages` — общие CRM-команды cli-core, одинаковые в каждом CRM-инструменте WireCat.
  Их списки и `show` читают локальное хранилище, поэтому сначала запустите `sync`; `--offline` теперь работает для них.
- Сделка или лид называется своим ref, `deal:12` или `lead:7`, как его печатает список, а не id или названием в
  Битрикс24.
- Сделка или лид отвечает `ref`, `pipeline` и `pipeline_name`, `stage` (ее имя), `status` (`open`, `won` или `lost`),
  `close_date`, `amount` как десятичной строкой в `currency`, оба `null`, если суммы нет, `assignee` как
  `<portal>/user/<id>`, а собственными полями портала — в `provider_metadata` по коду. `stage_id`, `pipeline_id`,
  `outcome`, `closes_on`, `assigned_to` и `person_ids` из них убраны; контакты лежат в `people`, компания — в
  `organization`.
- Их запрос списка принимает `status`, `stage`, `pipeline` и `organization`; свободное слово, временные окна и
  собственные поля портала из него убраны. `--all` убран из этих списков.
- `deals move <ref> <stage>` принимает стадию как аргумент, а не как `--stage`.
- У записи сделок и лидов нет `--body`. `--field <label or code>=<value>` задает пользовательское поле по описаниям,
  которые сохранил последний `sync`: поле-список принимает подпись или id своего варианта, поле с несколькими
  значениями — по одному `--field` на значение, а пустое значение его очищает. Код, который называет стандартное поле
  (`stageId`, `categoryId`, `assignedById`, `STATUS_ID` лида), отклоняется, как и `--field` без ключа перед `=`.
- Подпись пользовательского поля и подпись варианта списка сравниваются так, как cli-core сравнивает имена, для
  каждого `--field` и запроса: `е` находит `ё`, а буква, набранная двумя кодовыми точками, находит ту же букву,
  набранную одной. `people show` и `organizations show` так же сравнивают имя с совпадениями портала. Подпись, которая
  совпадала с одним полем, теперь может совпасть с двумя, и тогда она отклоняется с обоими.
- `fields list <deals|leads|people|organizations>` теперь из cli-core: он читает описания, которые сохранил `sync`,
  поэтому сначала запустите `sync`, и каждое поле называет свои части `untrusted`.
- `api.crm.deal.update` (и другие ключи `api.*` сделок и лидов) при `ask` теперь спрашивает и на `deals update`, `move`
  и `close`, а не только на `api call`. `--dry-run` записи сделки или лида называет каждый ключ, который она может
  проверить: ключ `api.*`, а также ключи перемещения, закрытия и `crm.assign-others` с параметром, при котором каждый
  из них применяется.
- `sync` читает описания полей портала для каждого вида, по одному лишнему запросу на вид, поэтому `--max-pages`
  доходит до записей позже. Вебхук без прав на их чтение все равно синхронизируется; любая другая ошибка там
  проваливает синхронизацию.
- Лиды стоят в одной воронке с именем `Leads`, потому что у лидов Битрикс24 воронок нет.
- `deals.delete` и `leads.delete` по умолчанию равны `ask`; `api call`, который задает стадию, проверяет `deals.close`
  (или `leads.close`) вместе с `deals.move`.
- `mcp` и `doctor` — общие команды cli-core: `mcp` добавляет `config`, `add` и `check`, а также `--profiles` и
  `--permission` у `serve`; `doctor` добавляет `--online`.
- `--body` или метод `api call`, которые можно прочитать больше чем одним способом, отклоняются до отправки: тело,
  которое называет одно поле дважды в любом написании, `entityTypeId`, который не простое число, `fields`, который не
  объект, метод с любым суффиксом, кроме одного `.json`, и метод `crm.item` без `entityTypeId`. Отправляйте каждое
  поле один раз, в одном написании.
- `--operation-id` убран из всех записей. На живом портале создание, повторенное с тем же id, создало вторую запись,
  поэтому повтор никогда не безопасен: после `outcome_unknown` выполните `sync` и `show` и повторите запись, только
  если ее там нет. Запись сделки или лида с `--operation-id` отклоняется до отправки.

### Исправлено

- `sync` после первого работает. Он спрашивал портал об изменениях со временем, которое портал отклоняет, поэтому
  каждый вид завершался ошибкой и ничего нового не копировалось. Время в фильтре теперь уходит в целых секундах со
  смещением, и это же исправляет `updated_at:` и `created_at:` в `people list` и `organizations list`.
- Запись, на которую пришел ответ об ошибке сервера или шлюза (500, 502, 504), — это `outcome_unknown`, а не
  `provider_unavailable`: портал мог ее выполнить. Запись, прерванная отменой, — тоже `outcome_unknown`, никогда не
  `cancelled`.
- Стадии читаются страница за страницей: справочник длиннее первых 50 строк REST 2 терял свои последние стадии.
- Id или ответственный, который не является числом, отклоняется до отправки; раньше он уходил пустым.
- `--body` сохраняет целые числа больше 2^53 как введены; `api call --body -` читает тело из stdin.
- Запрос без ответа прерывается через 10 секунд, а не через 30, чтобы чтение можно было повторить до того, как
  истекут собственные 30 с разовой команды.
- `show` для людей и организаций завершается ошибкой, если подписи полей портала не получены по причине, отличной от
  нехватки прав, а не показывает запись без подписей.

### Безопасность

- Проверки прав в `api call` и в записи `people` и `organizations` читают тело ровно в том виде, в каком оно
  отправляется, поэтому проверяют тот ключ, который нужен записи.
- Чтение через `api call` проверяет те же ключи, что и команды, которые читают эти записи, как уже делала его запись.

## 0.4.0 — 06.11.2026

### Добавлено

- `create` и `update` для сделок, лидов, людей и организаций принимают `--field "<label or code>=<value>"`, повторяя
  его для других полей или для каждого значения поля с несколькими значениями. Подпись ищется на портале; два поля с
  такой подписью отклоняются с их кодами. Поле-список принимает подпись или id своего варианта. `--field` важнее
  `--body` для того же поля, а `--title`, `--name`, `--first-name` и `--last-name` важнее обоих. Остальные значения
  уходят на портал как введены. `--dry-run` имена не ищет.
- `list` для сделок, лидов, людей и организаций фильтрует по собственным полям портала: `<code or label>:<value>`,
  для полей, по которым портал умеет фильтровать; поле-список принимает подпись или id своего варианта. Подпись с
  пробелами пишется `lead_source:web` или `Lead\ source:web`.
- `list --json=…,provider_metadata.<code>` добавляет это пользовательское поле к каждому элементу так, как его выдает
  `show`; `--json=…,provider_metadata` добавляет все. Запрашиваются только коды, которые перечисляет портал.
- `fields list <deals|leads|people|organizations>` перечисляет пользовательские поля портала этого вида: код, подпись,
  тип, держит ли поле несколько значений, может ли список по нему фильтровать, а для поля-списка — его варианты с их id.

### Изменено — может сломать вызовы

- `show` выдает значение поля-списка подписью его варианта, а не id; id переезжает в `option_id` рядом. Поле с
  несколькими вариантами выдает и то, и другое массивами.
- `api call` работает по списку разрешенного. Чтение CRM, каталога и пользователей и запись четырех типов CRM
  разрешены, как и раньше. Любой другой метод спрашивает, поэтому без терминала ему нужен `--yes`, а семейства,
  которые пишут людям, публикуют или отправляют данные наружу, запрещены: `imconnector`, `log.blogpost`, публичные
  ссылки на файлы и `event.bind` присоединяются к `im`, `imopenlines` и остальным. `api show` называет уровень каждого
  метода.

### Исправлено

- `deny` в профиле снова останавливает команду чтения. `b24` передавал cli-core только `resolveSettings`, поэтому
  cli-core никогда не видел таблицу прав b24: `deals.list: deny` не останавливал `deals list`, в том числе через MCP,
  а с любым ключом b24 в настройках каждый `--dry-run` падал с «names no command».
- `api.crm.<type>.add` и `api.crm.<type>.update` теперь действуют на `create`, `update` и `move` у `deals`, `leads`,
  `people` и `organizations`, как ключи команд уже действовали на `api call`. `--dry-run` называет их рядом с
  собственным ключом команды.
- `api call --dry-run` называет каждый ключ, который проверяет вызов, с его уровнем, например `api.crm.deal.delete`
  при `ask`, вместо «no key, allowed».
- `api call crm.item.add|update|delete` с `entityTypeId` от 1 до 4 проверяет ключ команды лида, сделки, контакта или
  компании, как уже делал `crm.deal.update`: `deals.delete: deny` теперь останавливает `crm.item.delete` для сделки.
- Каждый метод, имя которого заканчивается на `delete`, спрашивает, а не только перечисленные. Имя метода заглавными
  буквами или с суффиксом `.json` читается как его простое имя, поэтому больше не обходит ключ.
- Запись, которая задает стадию, проверяет `deals.move` или `leads.move`: `update` и `create` со `stageId` в
  `--body`, в том числе через MCP, и `api call` со `STAGE_ID` или `STATUS_ID` лида. `ASSIGNED_BY_ID` проверяет
  `crm.assign-others`, как и `assignedById`.
- Запись отправляется один раз. Запись REST 3.0, на которую не пришел ответ, отправлялась до трех раз еще с тем же
  `Idempotency-Key`, что на живом портале еще не проверено; теперь она сразу становится `outcome_unknown`, и ее
  сообщение один раз называет `--operation-id`.
- `pipeline_id:0`, воронка по умолчанию, принимается в `deals list` и `stages list`.
- Список разрешенного, как и до него, оставляет отклоненным чтение запрещенных семейств: `crm.activity.list`,
  `im.*`, `tasks.*` и остальные — `deny`, и `api show` так и говорит.
- Сервер MCP применяет таблицу прав b24 (WC-PERM-23): команда, которую профиль запрещает, показывается в поиске
  инструментов как недоступная, а не предлагается как доступная.

## 0.3.0 — 06.11.2026

### Изменено — может сломать вызовы

- `show` для сделок, лидов, людей и организаций выдает каждому пользовательскому полю его название на портале:
  `provider_metadata` сопоставляет коду поля `{ "label", "value" }`. `label` равен `null`, если у портала нет
  названия для поля или он не отвечает на запрос названий; `show` при этом все равно отвечает.

## 0.2.0 — 06.11.2026

### Исправлено

- Команды, которые обращаются к порталу, теперь выполняются внутри запуска cli-core: `meta.run_id` каждого ответа
  называет запуск, который находит `runs show`, с запросами к порталу в нем, `meta.duration_ms` измеряет команду, а
  `--timeout` останавливает зависшую команду. Переопределения прав агента MCP теперь тоже доходят до этих команд.
- `show` для сделок, лидов, людей и организаций больше не перечисляет пользовательские поля портала без значения:
  `provider_metadata` пропускает `null`, `""` и `[]` и сам пропускается, если ничего не осталось.

## 0.1.0 — 06.11.2026

### Исправлено

- Причина ошибки, которую определяет и более новый cli-core, больше не роняет каждую неудачную команду вместо того,
  чтобы напечатать ее ошибку.

### Добавлено

- Создан из `@wirecat/cli-template` 0.14.0.
- Клиент REST API Битрикс24 через входящий вебхук: REST 3.0 для сделок, лидов, контактов и компаний, REST 2 для
  остального; ограничения частоты портала соблюдаются и выжидаются; запись повторяется только с
  `Idempotency-Key`; секрет вебхука не попадает ни в одну ошибку и запись запуска.
- `session start | status | end` для каждого профиля и `session list`: адрес вебхука читается скрыто или из stdin,
  проверяется на портале и хранится в связке ключей под `bitrix24-cli`; `session status --check` показывает, чьи
  права у вебхука.
- `list` и `show` для `deals`, `leads`, `people` (контакты), `organizations` (компании), `pipelines`, `stages`
  (с исходом каждой стадии), `products` и `users`, напрямую с портала. Список принимает запрос, который становится
  собственным фильтром портала; свободное слово в нем совпадает с частью названия или имени. Имя, общее для двух
  записей, отклоняется, и обе показываются как кандидаты.
- `create` и `update` для `deals`, `leads`, `people` и `organizations`, а также `move` для сделок и лидов: каждая
  запись отвечает своим `operation_id`, который Битрикс24 получает как `Idempotency-Key`, поэтому `--operation-id`
  безопасно повторяет запись; `--dry-run` показывает ее заранее; назначение записи другому сотруднику запрещено, пока
  его не разрешат (`crm.assign-others`).
- `api list`, `api show <method>` и `api call <method> --body <json>`: любой метод Битрикс24, на той версии REST, где
  он находится, с проверкой `api.<method>` и ключа команды, которая делает то же самое; запись сообщений,
  автоматизации, задач и `batch` запрещена, пока ее не разрешат.
