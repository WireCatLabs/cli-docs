Заметные изменения в `@wirecat/mail-cli`. По одному разделу на версию, новые сверху.

## 0.32.0 — 14.11.2026

### Изменено — может сломать вызывающий код

- **Уровень `readonly` больше не останавливает `mail sync`** (cli-core 0.662.0, было 0.661.0). Команда, которая только
  загружает почту в локальное хранилище, работает на уровне `readonly`; `deny` по-прежнему её запрещает. Команды,
  которые пишут файлы владельца или обращаются к другому сервису, `readonly` по-прежнему блокирует. Если профиль
  останавливал синхронизацию уровнем `readonly`, поставьте этому ключу `deny`.

## 0.31.0 — 14.11.2026

### Исправлено

- **`rules import --format gmail` принимает `--yes` через MCP.** Агент мог только просмотреть правила, которые
  предлагают фильтры Gmail: инструмент предлагал лишь собственные параметры команды, а `--yes` принадлежал программе.
- **`rules export` отвечает через MCP.** Вызов падал с ошибкой «команда напечатала ответ вместо того, чтобы передать
  его». Теперь агент получает файл правил как ответ; в терминале и в конвейере команда по-прежнему печатает сам файл,
  поэтому `rules export > rules.json` импортируется обратно.
- **`rules apply` больше не предлагает повторить с тем же лимитом времени запуск, который ничего не прочитал.**
  Через MCP шаг предлагал передать более длинный `--timeout`, чего агент сделать не может, и был помечен как безопасный
  для запуска без вопроса, поэтому продолженный запуск мог повторяться без продвижения. Через MCP он теперь говорит
  владельцу дать серверу более длинный `MAIL_TIMEOUT` или запустить команду в терминале; в терминале шаг добавляет
  `--timeout 30m` и ждёт владельца.
- **`messages delete --rules` сохраняет почту от отправителя, которому писал владелец.** Команда судила об
  отправителях по сохранённой почте, где собственные письма владельца из папки «Отправленные» по IMAP выглядели
  полученными. Поэтому конверт от человека, которому владелец ответил, мог попасть в предложение для корзины, а
  готовое правило всё ещё могло поймать такого отправителя. Теперь cli-core помечает сохранённые письма владельца как
  отправленные, и причины очистки «ответил» и «писал» работают и для почтовых ящиков IMAP.

## 0.29.0 — 14.11.2026

### Добавлено

- **`rules apply --cursor` продолжает с места, где остановился прошлый запуск.** Запуск, который дошёл до лимита
  времени, отвечает `state: partial` с курсором и шагом, который продолжает работу. Запуск, который завершает окно,
  сообщает счётчики за всё окно.
- **`rules apply` принимает `--yes` через MCP.** Агент мог только просмотреть результат: инструмент не предлагал
  `--yes`.

### Исправлено

- **`rules apply` завершается на большом почтовом ящике, а через MCP отвечает вовремя.** Команда падала через 27 секунд
  на ящике из 17 000 писем, список которых читается около 4 минут. Теперь по умолчанию она работает до 15 минут (через
  MCP — 45 секунд, потому что клиенты сдаются примерно через минуту; `--timeout` по-прежнему задаёт лимит). Она читает
  заголовки от новых к старым и сохраняет работу пакет за пакетом, так что остановленный запуск сохраняет сделанное.
  `score:` и `--kind` судят об отправителе по его почте в хранилище, поэтому место остановки запуска никогда не меняет
  их решение.
- **`rules apply` сообщает, когда исчерпывает лимит времени.** Ошибка говорила, что почтовый сервер не ответил вовремя.
  Теперь она говорит, что команда дошла до лимита времени, и предлагает запустить её снова с более длинным `--timeout`.

## 0.26.0 — 13.11.2026

### Добавлено

- **`rules add --do meeting-notes:<provider>` сохраняет конспекты встреч как встречи.** Каждое письмо, под которое
  подходит правило, хранится целиком, защищено и при синхронизации ещё и сохраняется как встреча этого провайдера,
  связанная с событием календаря в той же комнате в тот же день. Без условия правило выбирает отправителя провайдера:
  `--do meeting-notes:telemost` — это `keeper@telemost.yandex.ru`. `rules apply --yes` сохраняет конспекты, пришедшие
  до правила; его пробный запуск их считает. `rules list`, `export` и `import` переносят этот флаг.

### Изменено — может сломать вызывающий код

- **Построен на cli-core 0.651.0** (было 0.648.0). Отсутствующий вход OAuth теперь имеет причину `session.missing`
  (было `oauth.missing`), `ai.address-refused` теперь `model.address-refused`, а устаревший отпечаток проекта встреч
  завершается с `conflict` вместо `configuration_error`. Первый экран показывает `pbx`, инструмент для Asterisk. Что
  изменилось в промежутке, описано в [журнале изменений cli-core](https://github.com/WireCatLabs/cli-core/blob/main/CHANGELOG.md).
- **Построен на cli-core 0.648.0** (было 0.647.0). Имя профиля, которого нет ни у одного профиля, теперь завершается с
  кодом 6. `store reset` больше не предлагается через MCP. Что изменилось в промежутке, описано в
  [журнале изменений cli-core](https://github.com/WireCatLabs/cli-core/blob/main/CHANGELOG.md).

### Исправлено

- **Два входа, завершившиеся одновременно, сохраняют обе записи.** `sign-ins.json`, который читает `doctor`,
  меняется под блокировкой, поэтому запись одного профиля больше не перезаписывает запись другого.

### Безопасность

- **`contracts/wirecat.json` перечисляет хосты, к которым cli-core обращается для почты**: npm для `upgrade`, а также
  Hugging Face и GitHub для загрузки моделей и хосты, на которые они перенаправляют. WireCat Desktop показывает их до
  установки mail.
- **mail обращается только к объявленным хостам.** Вход, проверка аккаунта Google, поиск сервера и запросы к реестру
  для оценки отправителя идут через `hostFetch`, который отклоняет любой другой хост до отправки первого байта и
  проверяет каждое перенаправление. Файл обнаружения или реестр, перенаправляющий на другой хост, больше не
  используется: поиск сервера пробует следующий источник, а запрос к реестру считается неудачным и повторяется при
  следующем запуске. Пакет поставляется с `contracts/wirecat.json`, поэтому WireCat Desktop показывает эти хосты до
  установки mail.

### Изменено — может сломать вызывающий код

- **Построен на cli-core 0.647.0** (было 0.630.0). При первом открытии хранилище переходит на более новую версию

  построение векторов, отклоняет адрес не на этом компьютере до отправки. Обычный `http://` теперь принимается только
  для этого компьютера, чтобы записи никогда не шли по сети без шифрования; используйте https или запускайте модель
  локально.

## 0.23.1 — 08.11.2026

### Добавлено

- **`MAIL_READ_ONLY` пропускает `rules add`, но в узких рамках**, чтобы плановый разбор почты в memo мог отправлять
  письма отправителя в конверты: только `--sender` или `--list-id` с `--do envelope`, только если правила с такими
  условиями еще нет, и с записью `source: agent`. `--domain`, `--filter`, `--kind`, любое другое действие или тег,
  замена правила, `rules remove|import|apply` и любое изменение на почтовом сервере по-прежнему отклоняются.

### Исправлено

- **`sync --rescan`, остановленный лимитом запросов, теперь говорит об этом и подсказывает, как продолжить.** Лимит
  задает `--timeout` (около 85 запросов по умолчанию), а `--max-pages` может его только уменьшить, поэтому большой
  `--max-pages` выглядел так, будто его не учли. Повторный запуск того же `--rescan` начинает снова с самой новой почты
  и до самой старой не доходит. Подсказка и следующий шаг теперь называют лимит и предлагают запустить `sync` без
  `--rescan`: он продолжит с того места, где запуск остановился.
- **cli-core 0.618.0 (было 0.614.0).** После `store recover run` (из memo, tg, max или wa) восстановленное хранилище
  заставляет каждую папку почты забыть UID, которые она перечислила после последнего сохраненного письма, начиная с дня
  до последней успешной глубокой проверки. Следующий обычный `mail sync` снова читает эту почту, и `--rescan` для этого
  больше не нужен.

## 0.22.0 — 08.11.2026

### Добавлено

- **`session start --method oauth` подключает новый профиль Gmail через приложение Google от WireCat.** Свой клиент
  Google Cloud не нужен, а `--client-file` по-прежнему указывает ваш. Пока Google не закончит проверку, он может
  показать экран «непроверенное приложение». `--method app-password` спрашивает пароль приложения, это способ по
  умолчанию для Gmail. `--method` задает способ входа только для нового профиля. У существующего его меняют через
  `config set auth`.
- **`mail <profile> account remove --keep-data|--delete-data`** удаляет профиль с этого компьютера: выходит из
  аккаунта (вход в Gmail через OAuth также отзывается в Google, и это может завершить другие входы того же приложения
  Google, как делает `session end --revoke`), удаляет пароль приложения или данные входа из связки ключей, забывает
  профиль в настройках и его запись о входе, а с `--delete-data` еще и удаляет сохраненную почту и журналы изменений.
  С `--keep-data` почта остается доступной для поиска. Старая запись Himalaya в связке ключей не затрагивается, другие
  профили остаются как есть.

### Исправлено

- **`account remove` больше не отзывает доступ Gmail, которым пользуется другой профиль.** Google отзывает доступ для
  всего аккаунта Google и приложения сразу. Поэтому, если другой профиль входит в тот же адрес (в любом регистре) через
  Google OAuth, отзыв пропускается: ответ дает `revoked: false` и сообщает "Google access kept: profile <name> uses the
  same address".
- **Подсказки для Gmail ведут на страницу паролей приложений и называют пароль 16-буквенным.** `session start` теперь
  дает ссылку <https://myaccount.google.com/apppasswords> вместо справочной статьи (она осталась в разделе "Sources") и
  пишет "16-letter password", потому что пароли приложений Gmail состоят из букв.

## 0.17.0 — 06.11.2026

### Добавлено

- **mail работает на cli-core 0.587.0 и cli-base 0.80.0.** `messages reset --holder <name> --since-time <time> | --last
  <n>` позволяет владельцу сдвинуть отметку агента назад, и следующий `review --holder` снова выдает ему эту почту
  (`--dry-run` сначала считает). `review --holder` выдает ключ находок и пропускает рассылки, а не всю массовую почту.
  `schedule list` показывает лимиты стоимости каждого расписания агента. Общее хранилище переходит на версию 52 (сделки)
  при первом открытии в mail, и более старый инструмент WireCat по-прежнему его читает.
- **`messages restore --write <id>` отменяет одну запись запуска и оставляет остальные.** Id это `operation_id`, который
  ответ запуска перечислил в `writes`. Последующее восстановление всего запуска отменяет остальное. Запуск, записанный в
  журнал до того, как у записей появились id, или id, которого в нем нет, отклоняется как `not_found`
  (`mail.write-unknown`).
- **`drafts send` указывает удаление черновика из «Черновиков» в `writes`** (`op: "delete"`), со своим
  `operation_id` рядом с id отправки. **Восстановление Gmail из корзины указывает возврат меток** как запись `label`,
  которая называет отменяемую запись, и журнал изменений ее хранит. Обе записи выполнялись и раньше, но без id в ответе.
- **Каждая запись отвечает своим `operation_id`, и журнал изменений его хранит.** Изменения `messages`, `messages
  delete` и `messages restore` перечисляют `writes`: по одной записи на каждую запись на сервер, с ее `operation_id`, тем,
  что она сделала (`op`), папкой, `to` для перемещения и числом писем. Запись восстановления также называет запись,
  которую она отменяет (`undoes`). `folders create|rename|delete` и `drafts create|update|delete` выдают `operation_id`
  своей записи. Те же id есть в журнале отправки.
- **`account inspect` и `messages import` говорят, в каком часовом поясе они читают `--since-time`.** Ответ дает
  `meta.timezone` и окно в UTC (`meta.window.since`), как это делает `sync`. `messages import` также дает
  `timezone` рядом с `since`, а `account inspect` добавляет строку в свою таблицу.

### Изменено — может сломать вызывающий код

- **`sync` сообщает, когда оставляет сохранённые правила без внимания**: `rules_unread` и `rules_unread_why` (например,
  `condition label`) в ответе и проблема `mail.rules-unreadable`, когда в правилах есть условие, которого эта почта не знает.
- **`sync --rescan` завершается ошибкой на заблокированном или повреждённом хранилище**, а не сообщает, что перенос в цепочки
  выполнен.
- **Имя файла вложения очищается так, как очищают скачивания cli-core**: символы направления и нулевой ширины, маскирующие
  расширение, убираются, а в Windows зарезервированное имя (CON, NUL, …) заменяется на `attachment-<n>`.

### Изменено — может сломать вызывающий код

- **`sync` читает «Вся почта» в Gmail, если профиль не называет папок.** Архивная почта Gmail уходит из INBOX, поэтому sync
  одного INBOX принимал её за удалённую. «Вся почта» находится по роли, так что работает и аккаунт Gmail на другом языке.
- **Заголовки читаются так, как их читает memo.** `List-Id` рассылки хранится без угловых скобок и в нижнем регистре, а

  видят одни и те же поля в обоих инструментах.

### Исправлено

- **`sync` применяет сохранённые правила почты аккаунта, как memo.** Правило пропуска или конверта, принятое в memo, теперь
  действует и для `mail sync`, и оба инструмента хранят одну и ту же сохранённую позицию, в которой есть отпечаток правил.
  Профиль Gmail синхронизируется в режиме Gmail, как у memo.
- **Метки Gmail называются так, как их называет memo** (`Inbox`, `Sent`, `Starred`, декодированные имена), поэтому
  сохранённые ящики `label:Inbox` продолжают совпадать, и ничто не хранится как `label:\Inbox`.
- **`sync --rescan` переносит ответы, сохранённые версией 0.1, в их цепочку** на сервере без id цепочек, например на Яндексе.
  Ответ говорит, сколько, в `rethreaded`. Цепочки Gmail не затрагиваются.
- **Ответ сохраняется в своей беседе на серверах без id цепочек, например на Яндексе и Mail.ru.** Цепочка — это первое
  письмо, названное в References, иначе в In-Reply-To. Почта, сохранённая раньше, переносится через `sync --rescan`
  (выше). Gmail сохраняет свои id.
- **Каждая команда, которая обращается к серверу, ограничена сроком запуска и Ctrl-C.** `session start` и
  `session status --check` открывали ящик сами, без срока и отмены, которые были у остальных команд, и источник мог
  переподключиться после закрытия.
- **`sync` просит не больше 20 МБ тел писем за один запрос**, а также не больше 15 писем, поэтому пакет крупных вложений не
  держит соединение минутами и не заполняет память.
- **Схемы `account check` и `session status` называют `file` источником пароля.** Пароль в закрытом файле отвечал `file`,
  тогда как опубликованная схема допускала только `environment`, `keyring` и `himalaya`, поэтому клиент, сверяющий ответы со
  схемой, его отклонял.
- **`sync`, остановленный `--limit`, говорит об этом.** Он отвечает `stopped: "limit"` и сколько новых писем оставил в
  `remaining`, а его следующий шаг говорит, что запуск сохранил письма, которые позволяет `--limit`, а не что остановился,
  чтобы ответить вовремя.

## 0.1.0 — 31.10.2026

### Добавлено

- **`mail` читает почтовый ящик по IMAP в общее хранилище WireCat и никогда не меняет сам ящик.** `memo` и другие
  инструменты WireCat затем ищут и читают эту почту на вашем компьютере. `mail` не отправляет почту.
- **`session start` входит в профиль по паролю приложения.** Новому профилю нужен `--address`, а в терминале адрес
  спросят сами. Сервер находится по встроенной таблице (Яндекс, Gmail, iCloud, Mail.ru, Fastmail), по записи MX, по
  ISPDB Thunderbird и по файлу autoconfig домена; `--provider` или `--host` вместе с `--port` и `--security` задают его
  вручную и пропускают эти поиски. Команда показывает шаги подготовки ящика, спрашивает пароль приложения без эха (или
  читает `MAIL_PASSWORD`), проверяет его на сервере и только потом сохраняет профиль, а пароль кладёт в связке ключей
  ОС. Без терминала она ничего не спрашивает и называет недостающий параметр или переменную. Пароль приложения, который
  Himalaya уже хранит в связке ключей, используется, если у `mail` своего нет. Шаги для каждого провайдера описаны на
  странице [Подготовка почтового ящика](https://github.com/WireCatLabs/mail-cli/blob/main/docs/providers.md). Outlook и
  Microsoft 365 принимают только OAuth, поэтому `session start` пока отказывается с ними работать.
- **`session status`, `session end` и `session list` управляют входом.** `session status --check` входит на сервер и
  доказывает, что пароль ещё работает; `session end` забывает пароль и оставляет синхронизированную почту; `session list`
  не требует профиля и показывает профили на этом компьютере.
- **`account check` и `folders list`** входят на сервер и показывают, что он поддерживает, а также папки с их ролью и
  числом писем.
- **`sync` читает новую почту в общее хранилище и пропускает то, что там уже есть.** Если `--folder` или профиль не
  называют другие папки, читаются INBOX и Sent, сначала новые, начиная с `--since-time` (по умолчанию последние
  30 дней). Одна дата начинается с местной полуночи, а в ответе указаны часовой пояс и окно в UTC. `--limit` ограничивает
  число новых писем за один запуск, `--rescan` заново перечисляет всё окно. Сохраняются текст и заголовки, вложения не
  сохраняются.
- **Большой ящик синхронизируется за несколько запусков.** `sync` тратит бюджет запросов, рассчитанный по сроку (15 минут
  в терминале, 45 секунд через MCP; `--timeout` и `--max-pages` меняют его), сохраняет после каждой части и отвечает
  `state: partial` с командой для продолжения. `mail <profile> status` показывает, как далеко продвинулась синхронизация,
  в том числе пока она идёт. Если часть писем осталась непрочитанной или удаления не проверялись, ответ сообщает об этом
  в `meta.issues`.
- **`sync` переживает ненадёжный сервер.** Оборванное соединение открывается заново после короткой паузы, и запуск
  продолжается; письмо, на которое сервер сейчас не может ответить, запрашивается ещё раз в конце запуска и остаётся
  на следующий. На сервере без идентификаторов писем, например на Яндексе, каждое новое письмо скачивается один раз, а
  уже сохранённая почта не читается заново.
- **ИИ-агенты работают с `mail` через MCP и навык.** `mail <profile> mcp serve` предлагает агенту команды профиля по
  stdio или по HTTP за вашим собственным туннелем с `--http`; что можно запускать, решают разрешения профиля, а
  `--permission` лишь ужесточает их. `mail skill install` устанавливает инструкции инструмента для Claude Code, Codex,
  Gemini CLI и OpenClaw, а для Hermes — с `--for hermes`.
- **Если связка ключей не работает, пароль приложения попадает в закрытый файл, и об этом не спрашивают.**
  `session start` кладёт пароль в `credentials.json` (режим 600) в папке настроек, один раз сообщает об этом в stderr и
  отвечает `credential_storage`. `--credential-storage file` выбирает файл сразу, но это не рекомендуется.
  `session status` может ответить `password_from: "file"`.
- **Запуск с перенесёнными папками никогда не удаляет пароль приложения владельца из связки ключей ОС.** Такой запуск
  читает пароль владельца, но не заменяет и не удаляет его, а новый пароль кладёт во временную запись. `session end` для
  пароля владельца ничего не удаляет и отвечает `kept: "owners-sign-in"`.
- **`wcat mail` запускает инструмент, а `wcat --help` его перечисляет.** Пакет устанавливает `wcat-mail` рядом с `mail`,
  а `wcat-mail --wcat-describe` печатает для `wcat` имя, версию и описание инструмента.
- **`doctor --online` сообщает, опубликована ли более новая версия.** К почтовому серверу он не обращается.
- **Команды, общие для всех инструментов WireCat:** `doctor`, `commands`, `config`, `skill`, `runs` и `upgrade`.
