# Документация от пользовательской задачи к результату

Предложение после обсуждения 3 октября 2026. Две страницы реализованы локально на RU/EN/ES и включены в путь после установки. Для технических страниц установки добавлен общий интерактивный блок над справкой. Первый пилот поведения агентов и записи команд — в [agent-evals](../agent-evals/README.md).

## Путь после установки

Установка → подключение агента → **Первые задачи** → **Как формулировать запросы** → справочник нужных команд.

Название «Первые задачи» помогает сразу начать пользоваться продуктом. «Как формулировать запросы» отвечает на конкретный вопрос; отдельное название «Советы» слишком неопределённо. Доступ к обеим страницам нужен из конца установки и подключения агента. В навигации они идут рядом с этими руководствами, до полного справочника мессенджеров.

Пользователь сообщает цель, область, период и ограничения. Агент обнаруживает команды и выбирает аргументы. Примеры команд полезны для понимания происходящего и самостоятельной работы в терминале; пользователю не нужно перечислять их в каждом запросе.

## Первая страница: «Первые задачи»

Начало должно ориентировать через действие:

> После входа попросите агента разобрать входящие, найти сообщение или собрать контекст к встрече. Начните с одной задачи только на чтение. Для поиска по прошлой переписке может понадобиться загрузить историю выбранного чата: вход в аккаунт сам по себе её не скачивает.

Первый копируемый запрос:

> Используй tg CLI: покажи пять рабочих чатов и скажи, в каких входящих от меня ждут ответа. Только читай; ничего не отправляй и не отмечай прочитанным.

Читатель должен увидеть пример результата, сообщения-основания и указание, какие чаты просмотрены. Наличие непрочитанного сообщения само по себе не доказывает необходимость ответа.

Следом — три разобранных диалога: поиск по истории, контекст к созвону, ответ по договорённостям. Каждый содержит исходный запрос, обнаружение источников, короткий ответ, follow-up пользователя и уточнённый результат. Команды раскрываются под репликами. Существующие семь сценариев лендинга дают темы и форму, но команды сверяются с опубликованной версией CLI и состоянием данных.

Остальные задачи удобнее дать кратким каталогом:

| Задача | Что пользователь получает | Что стоит уточнить в запросе |
|---|---|---|
| Входящие и новости | приоритеты и подборку источников | чаты/каналы, период, темы |
| Контекст к созвону | решения, актуальные риски, повестку | проект, участников, период, длительность |
| Поиск сообщения | найденный факт и его источник | чат/темы, приблизительные слова, время |
| Обещания и ответы | выполненные и открытые обязательства, черновики | чьи обязательства, срок, запрет отправки |
| Контакт по рекомендации | кандидатов и основания сравнения | услуги, валюты, страна, критерии выбора |
| Документы по теме | актуальный комплект и историю версий | проект, типы файлов, получатель/папка |
| Голосовое | расшифровку и просьбы собеседника | сообщение/отправитель, желаемый результат |
| Напоминания | сообщения по расписанию | дата, время, часовой пояс, адресат |
| Отправка ответа | подтверждённую отправку заданного текста | точный адресат и текст |
| Локальный экспорт | файл и ограничения доступной истории | период, папка, запрет сети |
| Клиентский бот | ответ с доступным контекстом заказа | бот, клиент, разрешённые источники, эскалация |
| Группа | вопросы без ответа и итоги обсуждений | группа, период, правила, допустимые действия |

Для каждой задачи: обещаемый результат → копируемый запрос → что нужно для выполнения → пример ответа → ограничение, влияющее на решение → ссылка на конкретную справку. На первой странице не нужны детали всех флагов, профилей и хранилищ.

## Вторая страница: «Как формулировать запросы»

Удобная формула: **что сделать + где искать + за какое время + какой результат нужен + что разрешено**. Для простого запроса достаточно задачи; остальные поля добавляются по необходимости.

### Найти факт в истории

> В чате «Atlas · команда» найди, какую сумму за аналитику мы согласовали в сентябре. Покажи сообщения с оценкой и подтверждением. Если истории не хватает, скажи, какой период нужно загрузить. Ничего не отправляй.

Когда нужна загрузка и пользователь разрешает её:

> Можно загрузить историю только этого чата начиная с 1 сентября. Сначала покажи оценку объёма, если загрузка большая.

В справочном раскрытии объяснить роли: `chats list` находит чат; `messages list` читает конкретное окно и сохраняет его; `store status` показывает имеющийся архив; `store fetch` заполняет ограниченную историю; `messages search` ищет локально; `messages context` проверяет окружение найденного сообщения. Даты поиска поддерживаются также фильтрами в строке запроса. Порядок зависит от состояния архива.

### Подготовиться к встрече

> Собери контекст по Atlas за последнюю неделю: решения, риски и вопросы. Проверь проектную группу, дизайн и мою личку с участниками. Отдели старые блокеры от текущих. Подготовь повестку на 20 минут; ничего не отправляй.

### Найти подходящий контакт

> Найди рекомендованного бухгалтера в чатах про фриланс или бизнес. Мне нужны международные платежи в евро и долларах и регулярное ведение. Сравни рекомендации, покажи источники и перечисли, что ещё нужно уточнить. Подготовь первое сообщение без отправки.

Страна регистрации, налоговый режим и способ получения платежей помогают задать вопросы кандидату. Отзыв о человеке с распространённым именем не подтверждает личность человека; агент не должен склеивать двух Елен без основания.

### Подготовить и затем отправить ответ

> Проверь, что Том уже прислал по макету, и подготовь ответ. Не отправляй.

Follow-up после просмотра черновика:

> Отправь этот текст Тому в личный чат, который ты только что нашёл. Другим ничего не отправляй.

При двух подходящих адресатах агент уточняет, кому писать. Новая задача не наследует неограниченное разрешение на будущие отправки.

### Найти актуальные файлы

> Собери договор, счета и презентацию Atlas из группы и лички Анны. Выбери согласованные версии, укажи основание выбора, старые покажи отдельно. При противоречии не выбирай молча. Пока не скачивай и не отправляй.

«Последний загруженный файл» и «финально согласованный» могут различаться. При необходимости следующим запросом пользователь задаёт папку и разрешает скачивание.

### Поставить напоминания

> В понедельник, 5 октября, напомни мне в 09:00 открыть повестку, а в 18:00 проверить решения по Atlas. Время Мадрида. Отправь напоминания в Избранное.

Слово «завтра» зависит от часов и часового пояса. Успех подтверждается результатом планирования. Неизвестный исход отправки требует проверки, а не слепого повтора.

Полезные ограничения для любой задачи: только чтение; только перечисленные чаты; заданный аккаунт; запрет сети; предел периода/объёма; черновик до подтверждения; источники для ключевых фактов. Использовать их там, где они меняют результат, не перегружать каждый простой запрос полным шаблоном.

## Установка: сначала понятный путь

Это правило относится и к общей установке портала, и к техническим страницам Telegram/MAX. Сейчас общая страница уже начинается с выбора мессенджера и блока InstallationGuide; страницы самих инструментов рано переходят к Node/Bun и списку требований.

Предлагаемое начало:

> Установите Telegram или MAX через локального агента либо в терминале. Агент поможет проверить компьютер, установить npm-пакет и подключить аккаунт. CLI работает на Windows, macOS и Linux. Коды входа вводятся в локальном терминале; после входа можно проверить аккаунт и прочитать первые чаты.

Дальше:

1. Выбор мессенджера и основной блок установки через агента с копируемым запросом. Возможность установить в терминале находится рядом.
2. Что произойдёт: проверка окружения → установка пакета → вход → проверка аккаунта/чатов → подключение агента. Кратко объяснить, что установка и вход обычно занимают несколько минут, а исторический архив загружается отдельно и зависит от объёма.
3. Как понять, что готово: агент/CLI видит нужный аккаунт и несколько чатов. При проблеме дать ближайший следующий шаг.
4. Первый полезный запрос и переход к «Первым задачам».
5. Самостоятельная установка: Node/npm, команды по ОС, Windows PATH, варианты входа и расположение файлов.
6. Разработка из исходников, служба, расширенная диагностика — в конце или в отдельных руководствах.

Технические страницы инструментов синхронизируются из релизов. Их содержательные изменения идут в tg-cli/max-cli, не в generated content/docs/tg или max. Общий интерактивный блок живёт в портале; Markdown инструментов может ссылаться на него. Вставлять JSX в обычные .md бессмысленно: интерактивный компонент требует .mdx.

## Как из документации получить улучшения CLI

Сначала наблюдаем проблему в записи и отделяем ошибку агента, слабое описание команд, недостаток данных, ограничение контракта и ошибку стенда. Дорогая последовательность команд без ошибочного ответа сама по себе не доказывает необходимость новой команды.

Первые гипотезы для проверки:

- Discovery должен объяснять, откуда берутся данные команды и что она покрывает. Одной метки «mutates» недостаточно для различения network read, local write и Telegram write.
- Агенту полезны узкая справка о выбранной команде, примеры аргументов, формат результата и связь с предварительным состоянием архива. Полное дерево `commands --json` не обязательно требуется целиком на каждую задачу.
- Пустой результат поиска при неполном архиве должен помогать выбрать следующий шаг: указать чат/период и предел имеющихся данных.
- Статус загрузки должен позволять проверить покрытие нужного периода, не только абстрактную полноту всей истории. В пилоте повторная загрузка не дала нового факта; это наблюдение симулятора, которое нужно проверить на настоящем store.
- Если несколько независимых прогонов устойчиво повторяют один сложный путь, проверить пользу составного действия или нового параметра ограниченной подгрузки. Нужны явные границы, оценка затрат и отсутствие неявной загрузки всех чатов/запуска службы.

Новые команды здесь не объявляются существующими. Публичные рецепты пишутся только на поддержанном контракте и с отмеченными предпосылками.

## Порядок работы

1. Зафиксировать задачи и состояния, запустить холодные пилоты, сохранить проверяемые записи — начато в agent-evals.
2. Расширить матрицу: неоднозначный адресат, второй page/cursor, stale/gapped archive, отказ permissions, неясный send outcome, конфликт версий файлов, offline и oversized evidence.
3. Проверить основной путь на настоящем CLI с синтетическим SQLite store и отдельным профилем. Сетевые сценарии требуют контролируемого provider/test adapter или отдельного тестового аккаунта; текущий симулятор их не доказывает.
4. Написать две пользовательские страницы на проверенных сценариях и обновить конец установки/подключения. Сверить все команды с выбранным релизом и перевести EN/RU/ES.
5. Обновить структуру установки портала и через отдельные изменения — страницы инструментов. Сохранить прежние heading anchors и проверить входящие ссылки.
6. По повторяемым провалам улучшать discovery/skill/CLI, сравнивая новый холодный прогон с тем же fixture и промптом. Предыдущая запись сохраняется для сравнения.
