# Установка с лендинга и первая настройка

## Что сделано в cli-docs

Обновление: [план документации](2026-10-02-docs-onboarding.md) переносит подробные инструкции
с лендинга в общий раздел установки. На лендинге остаются две короткие ссылки; в доках выбор
агента дополнен Hermes, Claude Desktop описан отдельно в MCP. Ниже — исходный этап работы.

- В хиро две отдельные кнопки: «Установка MAX» и «Установка Telegram».
- Каждая раскрывает выбор Claude Code, Codex, Gemini CLI, Cursor, Claude Desktop или «Другой».
  Пользователь копирует запрос агенту: проверить Node/npm, установить CLI, подключить skill/MCP,
  помочь войти, проверить результат. Есть отдельная инструкция для терминала.
- Windows: новый терминал после установки Node; `npm.cmd` при блокировке PowerShell-скриптов;
  `npm exec --yes --package=@leemour/<tool>-cli -- <tool>` при отсутствии глобального CLI на PATH.
- До начала агент сообщает: на настройку заложить около 5 минут; история может скачиваться дольше.
  Объём истории пользователь выбирает отдельно.
- `.github/workflows/windows-install.yml` проверяет опубликованные пакеты на Windows с Node
  22.16.0 и 24: глобальная установка в путь с пробелами, `.cmd`, `doctor`, дерево команд,
  миграция пустой SQLite-базы, чтение её схемы, установка обоих skills и повторная установка,
  `npm exec` без глобального PATH и запуск после добавления prefix в PATH текущего процесса.
  **Проверено 2026-10-03:** max-cli 0.22.0 и tg-cli 0.22.0 прошли все четыре задания на Node
  22.16.0 и 24.21.0; основной CI сайта также прошёл.
  [Результаты Windows](https://github.com/leemour/cli-docs/actions/runs/37078689619),
  [PR #9](https://github.com/leemour/cli-docs/pull/9) слит в main; повторный запуск после слияния
  прошёл все четыре задания.
  Вход в реальные аккаунты и работа keyring с настоящими ключами не проверялись.

## Можно ли установить кнопкой из браузера

Для текущего статического сайта практический путь — копируемая инструкция агенту или команда
для терминала. File System API даёт браузеру доступ к выбранным пользователем файлам, но не
предоставляет API запуска локального установщика. Произвольное выполнение команд потребовало бы
уже установленного локального приложения/расширения. Поэтому первая кнопка не может сама
установить CLI. См. [File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API).

`npm exec` помещает пакет в npm cache и добавляет его executables в PATH запущенного процесса:
это рабочий обход отсутствующего глобального prefix, а не постоянное исправление PATH.
См. [npm exec](https://docs.npmjs.com/cli/v11/commands/npm-exec/) и
[расположение executables npm](https://docs.npmjs.com/cli/v11/configuring-npm/folders/).

## Windows: что ещё сделать в CLI

Основной CI выполняется на Ubuntu. Telegram теперь автоматически проверяет onboarding PR на
Windows/macOS. Такой же запуск для MAX добавлен в [PR #351](https://github.com/leemour/max-cli/pull/351).
PR #351 слит; полный набор тестов и сборка прошли на Windows/macOS.
Windows workflow портала проверяет установку опубликованных пакетов, а не полный набор unit tests.
Проверка портала от 2026-10-03 подтвердила запуск на Windows, обход отсутствующего PATH,
SQLite и установку skills. Постоянное исправление пользовательского PATH пока не реализовано.

Следующий PR в каждом CLI:

1. Установка из `npm pack` на `windows-latest` до публикации, а не только выполнение исходников.
2. Проверка Node/npm, `.cmd` и global prefix, в том числе пути с пробелами.
3. Для tg — подсказки doctor при отсутствующем PATH по образцу max; для max проверить уже
   существующие подсказки. Исправление PATH — отдельное явное действие; сохранять прежние записи,
   не добавлять дубликаты, обновлять текущее окно и пользовательский PATH.
4. Проверить keyring/file fallback, создание SQLite store и установку skill в временные каталоги.
   Ни один тест не требует настоящего аккаунта.

## Нужен ли .exe

Пока оставить npm + инструкцию агенту. Отдельный `.exe` — следующий этап, если отсутствие Node
остаётся главным препятствием после проверки Windows. Это отдельный канал релизов: сборка,
нативные зависимости и assets, обновления, подпись, smoke checks на чистой машине. Сам `.exe`
не исправляет PATH; для этого нужен installer либо запуск по полному пути.
Node предоставляет [Single executable applications](https://nodejs.org/api/single-executable-applications.html),
но упаковку этих CLI необходимо проверить отдельным прототипом. Поддержка `.exe` сейчас не добавлена.

## Первичная команда настройки: следующий PR

Для Telegram реализован `tg setup --agent codex`:
[PR #229](https://github.com/leemour/tg-cli/pull/229). Команда проверяет каталоги, получает
ключи приложения, выполняет QR/phone-вход, проверяет пять чатов и устанавливает skill выбранного
агента. Повторный запуск использует сессию; JSON содержит один результат. История остаётся
отдельной командой после выбора чата и объёма. Отмена и общий таймаут закрывают соединение,
удаляют временный QR и отменяют ожидающий ввод.

Общий ввод получил AbortSignal в опубликованном cli-messaging 0.120.0
([PR #444](https://github.com/leemour/cli-messaging/pull/444)). Локально прошли 541 тест tg-cli,
покрытие, lint, typecheck, Bun, документация, parity и генерация команд; реальный аккаунт не
использовался. Все проверки PR прошли, включая полный набор тестов и сборку на Windows и macOS
([результаты](https://github.com/leemour/tg-cli/actions/runs/37082468779)). PR #229 слит в main.
Проверки Windows/macOS теперь запускаются автоматически на изменения onboarding и зависимостей.
Windows-прогон выявил и помог исправить сокращение home-пути, распознавание user docs и
Unix-only ожидания file mode; security docs описывают Windows ACL.

На npm tg-cli эта команда пока не выпущена и на лендинге не предлагается. Для MAX реализована
в [PR #351](https://github.com/leemour/max-cli/pull/351), по утверждённому владельцем плану.
Остальные пункты целевого сценария:

1. Проверить runtime, каталоги, наличие сессии, доступность CLI на PATH и подключение агента.
2. Сообщить человеку этапы и ориентир «около 5 минут», затем провести через вход; существующая
   сессия не требует нового входа. Установка skill — с выбором агента, запуск сервера — по выбору.
3. После входа показать список чатов и предложить объём первоначальной истории: пропустить,
   выбранные чаты/период. Полный архив не скачивать по умолчанию.
4. Выполнить ограниченный первоначальный fetch через существующие команды store/backfill,
   показать этап, число обработанных чатов и сообщений, ограничения сервиса, результат и команду
   продолжения. Не обещать скачать всю историю за пять минут.
5. В машинном режиме stdout — один результат JSON; этапы и подсказки — stderr.
   Не спрашивать интерактивно без TTY; параметры для автоматизации должны быть явными.
6. Проверки: свежая установка, повторный setup, отмена/продолжение, неправильный код,
   недоступная keyring, Windows, разделение stdout/stderr. Фейковые провайдеры, без живых аккаунтов.

## Telegram: существующий путь и улучшения

Проверено на документации release v0.21.0: `tg session start --app auto` уже получает существующие
ключи или регистрирует приложение за пользователя. Затем CLI выполняет QR-вход. При сбое
`tg session start --app browser` открывает my.telegram.org/apps, а ID/hash вводятся в терминале.
В исходниках `src/telegram/registration.ts` auto следует веб-формам my.telegram.org; это не
официальный API регистрации.

QR-вход тоже требует api_id/api_hash:
[Telegram QR login](https://core.telegram.org/api/qr-login). Регистрация своего приложения описана
в [Creating your Telegram Application](https://core.telegram.org/api/obtaining_api_id).
Поэтому перенос QR в браузер сам по себе не убирает этап ключей.

Реализовано в PR tg-cli #229:

- Показать два этапа: «1/2 приложение Telegram», «2/2 вход в аккаунт»; отличать код для
  my.telegram.org от кода входа в клиент.
- В setup предложить auto как простой путь, browser как альтернативу; не менять молча текущий
  default session start. При ошибке auto назвать этап и точную команду ручного продолжения.
- В browser-варианте дать последовательность: номер → код в приложении Telegram → API development
  tools → App title / Short name / Desktop → ID и hash в локальном терминале.
- Ключи, коды, пароли и session не собирать на wirecat.dev. Если понадобится локальная browser UI,
  спроектировать её отдельно с loopback-сервером, одноразовым токеном и проверкой Origin;
  регистрация приложения всё равно остаётся на my.telegram.org.

MAX setup использует существующие QR/token/Chromium/SMS пути и не меняет default `session start`.
Telegram setup реализован и слит в main; публикация новой версии tg-cli — отдельный шаг.
Локальная авторизация Telegram через browser UI не реализована.

## Выпуск и MAX: состояние 2026-10-03

Telegram 0.23.0 подготовлен в [draft PR #231](https://github.com/leemour/tg-cli/pull/231).
Все release checks и CI Linux/Windows/macOS прошли. В релиз входят также изменения отправки в
forum topics, поэтому release skill требует отдельного live-разрешения и существующий тестовый
forum с вторым тестовым аккаунтом. Владелец разрешил только smoke в Saved Messages.
Захваченные этапы прошли до планирования и списка сообщений; финальный вывод недоступен.
Оставшееся доставленное тестовое сообщение проверено по автору/времени, удалено; перечитывание
подтвердило отсутствие сообщений smoke. Полный smoke пока не отмечен как пройденный.

MAX PR #351 слит: guided setup, помощь и bundled skill до входа. После интеграции нового
shared runner прошли 1235 тестов, coverage, Bun, docs, parity и matrix (488 tested, 63 reason,
0 missing). Первый Windows CI выявил старые Unix mode assertions, separator classifier,
запуск Biome `.cmd` без shell и нестабильный HTTP burst test; исправления прошли CI Linux/Windows/macOS
([результаты](https://github.com/leemour/max-cli/actions/runs/37117782374)).
Реальный аккаунт MAX не использовался. Обе новые setup-команды пока не опубликованы на npm.

`npm install -g` создаёт Windows `.cmd` launcher, но не меняет пользовательский PATH.
Если npm global prefix отсутствует в PATH, агент использует документированный `npm.cmd exec`
и подсказки CLI. Автоматическое постоянное изменение PATH не реализовано.
