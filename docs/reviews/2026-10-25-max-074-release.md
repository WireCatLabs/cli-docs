# MAX 0.74.0 reviewed publication

Readers can fetch a bot's old chat history with `bot messages sync`, answer every join request of a channel at once
with `chats requests confirm|reject <chat> --all`, add a second webhook with `--append`, and see blocked commands in
the CLI and MCP catalogues with their availability instead of having them hidden. Scripts read `--jsonl` output as
`item` records and a final `end` record. The portal targets published max 0.74.0 (0.73.0 and 0.74.0 both covered)
with Core 0.412.0 and Base 0.51.0; the previous pin was v0.72.0. Reviewer: Claude.

  - `bot store` and `bot store fetch` are absent from the contract; `bot messages sync` has the same options. Running
    `max bot store fetch x` in the sandbox (`pnpm docs:cli`) printed `` `max bot store fetch` is not here — use `bot
    messages sync` `` (cli-core `cli/moved.js`).
  - A saved `permissions.bot.store.fetch` stops with `configuration_error` naming `permissions.bot.messages.sync`
    (cli-core `sends/permission-aliases.js`, `canonicalPermissions`).
  - `chats requests confirm|reject` take `[person]` and `--all`; `--all` counts the requests, passes the hourly-limit
    guard with that count and makes one MAX call. `--link` is not an option for max, and its client refuses a link
    because MAX does not report it (cli-core `services/admin.js`, max-cli `client/chat-writes.js`).
  - `bot webhooks set` has `--append`; `search runs` has only `--limit` and `--page` plus `started_at:` and other query
    fields; `contacts events` uses `at:` and `scope:` query fields.
  - `watch --json` refuses with "watch is a stream — use --jsonl" (max-cli `commands/watch.js`); connection status
    goes through the renderer's note (stderr). List `--jsonl` ends with `{"type":"end","complete",…,"page"}`
    (cli-base `standards/output.js`).
  - MCP discovery passes `includeUnavailable: true` (cli-core `mcp/server.js`, `mcp/bot/server.js`); availability
    has the documented `{ available, reason, permission }` shape (`cli/command-availability.js`). Commands left out of
    MCP are exactly the contract's `mcp: false` or `lifetime` set: `setup`, `session`, `complete`, `serve`, `watch`,
    `mcp`, `bot watch`, `bot mcp`, `bot auth`, `bot uploads put`. `upgrade` is wrapped in `grantsAuthority` unless
    `--check`, so the native table rightly drops it.

## Portal corrections

Retired, because 0.73/0.74 fixed the source: configuration-reference permission paths (`models.download`,
`doctor.reports.create`), diagnostics `search runs` MCP arguments, groups `confirm|reject` shorthand, and the mcp
`upgrade`/`complete` row.

Added, each with source and reason in `scripts/docs-corrections.json`:

- **usage** (ru/en/es): the native guide still says `--all` is refused and names `requests accept`. The package answers
  every request with `--all`, refuses only `--link`, and the command is `requests confirm`.
- **mcp** (ru/en/es): the tools table says `max_write` is absent when the profile permits no write. Because the
  catalogue now includes unavailable commands, `mcp/surface.js` registers `max_write` whenever a writing command
  exists; blocked writes are listed as unavailable and refused on call.
- **commands**: `max-bot-store` and `max-bot-store-fetch` anchors land on `max bot messages sync`.
- **changelog** (en/es): the new `<чат>` placeholder reads `<chat>`, as the other placeholders already do.

The strict example checker rejected the native groups row `chats requests confirm\|reject <чат> --all` as an unknown
option for the `chats requests` group, because it read options before seeing the alternative subcommands. It now
classifies a `\|` subcommand alternative as syntax before option checks, as it already did without options.
