Задача — одно дело, которое должны сделать вы или которое кто-то должен вам: вопрос, на который вы
не ответили, просьба, ваше обещание или обещание, данное вам. Эта страница помогает не терять такие
дела в чатах. Прочитав её, вы сможете попросить агента показать план на сегодня, превратить
сообщение в задачу, указать, кто должен её сделать, привязать к ней все относящиеся сообщения и
закрыть её, когда дело сделано. Задачи хранятся на вашем компьютере, в локальном хранилище `tg`, `max` и
`memo`. Ничто на этой странице не отправляет сообщений.

Категории, теги на задачах, ключи по типам, бронь задачи и проверка на дубликаты уже есть в общем
ядре инструментов (cli-core). В `tg` и `max` есть всё это; в `memo` пока нет брони задач и разбора
дубликатов.
Закрытия, которые ждут вас, когда агент не уверен, задачи-продолжения, список из 59 категорий и
проверка на дубликаты, которая читает привязанные сообщения, есть в `tg` и `max`; в `memo` их пока нет.
`tg` и `max` читают список категорий из общего файла настроек. В них первая синхронизация не открывает
задач из вашей истории, а задачи чата строятся по вашей просьбе (`tasks scan`). Они открывают в группе
задачи лишь по тому, что спрашивают у вас, и записывают, кто должен сделать задачу из сообщения.
Технические подробности — на странице [Как устроены задачи](./tasks-architecture.mdx).

## Откуда берутся задачи

- **Правила находят их в сообщениях — там, где что-то спрашивают у вас.** В `tg` и `max` всё решает вид чата:
  - **Личный чат:** каждый вопрос, на который вы не ответили, становится задачей типа `question`.
  - **Группа:** только вопрос, который отвечает на ваше сообщение. Вопросы других людей — не ваши
    задачи.
  - **Канал или «Избранное» в Telegram:** ничего.

  Сообщение с упоминанием вас становится задачей `mention` — в личном чате или в группе; упоминание
  должен отметить сам мессенджер, просто написанное имя не учитывается. Чат, вид которого инструменту
  неизвестен, считается группой. Правило автоответа с действием `task` открывает
  задачу `request` на каждое подходящее сообщение ([Telegram](./tg/replies.md), [MAX](./max/replies.md)).
  Правила работают, когда агент синхронизирует или разбирает ваши чаты, и пока инструмент работает в
  фоне (`messages sync`, `review` и `serve`). В `max` `serve` открывает только задачи правил автоответа;
  остальные правила сработают при следующей синхронизации или разборе. Правило выбирает категорию задачи по словам сообщения.
- **Группа под наблюдением даёт все вопросы.** Если вы хотите получать задачей каждый вопрос группы
  без ответа, кому бы он ни был адресован, поставьте группе тег `watch-tasks` (см.
  [Все вопросы группы](#все-вопросы-группы)).
- **Старые сообщения ждут вашего решения.** В `tg` и `max` первая синхронизация аккаунта не открывает
  задач из вашей истории. Следующие синхронизации открывают задачи из новых сообщений. Если вы хотите
  получить задачи из истории чата, агент сначала показывает, что откроется, и открывает это после
  вашего согласия; см. [Задачи из истории чата](#задачи-из-истории-чата).
- **Их добавляет агент или вы.** Обещание («пришлю договор в понедельник») или просьбу, которую не
  поймало правило, добавляют вручную, с типом `promise` или `request` и с категорией. Обещание,
  данное вам, добавляют так же, указав этого человека исполнителем; см.
  [Что вам должны другие](#что-вам-должны-другие).
- **Задачи проекта** живут в проекте и имеют ключ: ключ проекта и номер, например `HRB-12`. Их типы —
  `chore`, `bug` и `feature`. Их создают через `memo`; см. [Задачи и напоминания в Memo](./memo/tasks.md).

Правило закрывает задачу `question` или `mention`, когда вы отвечаете в чате. Если у сообщения уже
есть задача, повторное добавление вернёт её же.

## Попросите агента

```text prompt
Используй tg CLI. Синхронизируй мои чаты и покажи план задач: что просрочено, что нужно сделать сегодня и в каких чатах ждут моего ответа. Для каждой задачи покажи сообщения, из которых она появилась. Ничего не отправляй.
```

Вы получите короткий список: открытые задачи со сроками и чаты, где последним написал собеседник.
Каждая задача указывает на свои сообщения, поэтому видно, откуда она взялась. Для MAX напишите
«max CLI».

```text prompt
Используй tg CLI. В чате с Иваном Примером я обещал прислать подписанный договор до пятницы. Добавь задачу-обещание для этого сообщения со сроком в пятницу и понятным названием. Привяжи к ней более ранние сообщения, где мы договорились о цене.
```

```text prompt
Используй tg CLI. В чате с Иваном Примером он обещал прислать мне подписанный счёт до пятницы. Добавь это как его задачу со сроком в пятницу. Потом покажи всё, что мне должны другие.
```

```text prompt
Используй tg CLI. Покажи, какие задачи откроются из последних 300 сообщений моего чата с Иваном Примером. Пока ничего не открывай.
```

```text prompt
Используй tg CLI. Покажи задачи, которые агент предложил закрыть, с его причиной и уверенностью. Пока ничего не закрывай и не отклоняй.
```

```text prompt
Используй tg CLI. Пройди по списку задач, которые могут быть дубликатами. Объедини пары, которые явно об одном деле, отклони явно разные, а остальные отметь как неясные. Потом покажи мне только неясные пары.
```

## Одна задача — много сообщений

Задача начинается с одного сообщения — её источника. Более поздние сообщения о том же деле
привязываются к ней, и задача хранит всю историю. У привязки есть вид: `related-to` (по умолчанию),
`evidence` (сообщение показывает, что задача настоящая) или `created-from`. Задача может указывать
и на чат, человека, документ, заметку или веб-адрес.

В одном чате может быть много задач. Три разных вопроса, которые Анна Пример задала вам в одном
чате, — три задачи. Задача — об одном деле, а не об одном чате или одном человеке.

## Что вам должны другие

Задача — не только то, что должны сделать вы. Когда кто-то вам что-то обещает, например «пришлю фото
завтра», сохраните это тоже как задачу, а этого человека укажите её **исполнителем** — тем, кто
должен её сделать. Тогда можно спросить агента, что вам должны другие, и напомнить о просроченном. В
`tg` и `max` исполнители бывают у задач из сообщений; у задач проектов в `memo` — свои.

`tasks add` и `tasks update` принимают `--assignee`:

- `--assignee sender` — тот, кто отправил сообщение задачи.
- `--assignee person:<id>` — человек, которого вы называете. Несколько значений — несколько человек.
- `--assignee none` — убирает исполнителей.

Задача без исполнителя — это нормально: лучше, чем пропущенная задача. Если инструмент не знает
человека-отправителя, задача всё равно добавляется, без исполнителя.

`tasks agenda` показывает открытые задачи, которые вам должны другие, в разделе "assigned", сначала
самые старые; `tasks list "assignee:any state:open"` тоже их показывает.
`assignee:none` находит задачи без исполнителя, а `assignee:person:<id>` — задачи одного человека.
Агенты, которые работают через MCP-сервер, передают `assignee` в `tasks_add` и `tasks_plan`.

```text
tasks add msg:telegram/1/77/42 --type promise --category documents --assignee sender
tasks update PR-4 --assignee person:12
tasks update PR-4 --assignee none
tasks list "assignee:any state:open"
```

## Все вопросы группы

В группе правила открывают задачу только по вопросу, который отвечает вам, и по упоминанию вас. В
небольшой группе, где вы отвечаете за всё, например в группе с клиентом или в семейной, может
понадобиться каждый вопрос. Поставьте такой группе тег `watch-tasks`:

```sh
tg personal tags add --chat "Renovation" watch-tasks
tg personal tags remove --chat "Renovation" watch-tasks
```

Тег работает в `tg` и `max` и только для групп; канал задач не открывает никогда. Что он меняет:

- **Каждый вопрос, на который вы не ответили, открывает задачу, кому бы он ни был адресован.**
  Правило узнаёт вопрос по вопросительному знаку или по ответу на ваше сообщение.
- **Только новые сообщения.** Задачи появляются после каждой синхронизации, в `review` и, в `tg`,
  пока работает `serve`. Для старых сообщений группы используйте [`tasks scan`](#задачи-из-истории-чата).
- **Вопросы, а не все сообщения.** Просьба или обещание без вопросительного знака, например
  «пришли файл» или «сделаю завтра», правило задачей не делает. Их добавляет агент через `tasks add`,
  с `--assignee sender`, если это обещание самого отправителя.
- **Вопрос закрывает ответ любого участника.** Его закрывает ваш ответ, а также ответ на вопрос
  (reply) от любого участника, кроме того, кто спросил. Более позднее сообщение, которое не отвечает на
  вопрос, ничего не закрывает: такую задачу закройте сами или пусть её закроет агент с указанием
  уверенности; см. [Когда задачу закрывает агент](#когда-задачу-закрывает-агент).
- **Без исполнителя.** У задачи, которую открыло правило, исполнителя нет; агент может назначить его
  через `tasks update`.

Ставьте тег только группам, за ответы в которых отвечаете вы. Оживлённая группа с тегом даст много
задач.

## Как пользоваться задачами надёжно

**Чтобы лишних задач было мало:**

- Правила открывают задачи только там, где что-то спрашивают у вас: в личных чатах, а в группах —
  только ответ вам или упоминание вас. Каналы задач не открывают.
- Первая синхронизация не открывает задач из истории. Просматривайте историю чата только по своему
  выбору и читайте список, прежде чем добавить `--yes`.
- Ставьте тег `watch-tasks` только небольшим группам, за которые отвечаете вы.
- Проверка дубликатов не даёт открыть задачу, которая может быть той же работой, что уже открытая;
  агент вместо этого привязывает сообщение к ней.

**Чтобы ничего не пропустить:**

- В плане на день (`tasks agenda`) есть чаты, где последним написал собеседник, а вы не ответили, и
  чаты, где последним написали вы и вам не ответили. Они там, даже если задачи нет.
- Попросите агента каждый день читать новые сообщения и добавлять то, чего правила не видят: просьбы
  и обещания без вопросительного знака — ваши и чужие.
- Храните то, что вам должны другие, как задачи с исполнителем. План на день показывает их в разделе
  "assigned", сначала самые старые.

```text prompt
Используй tg CLI. Синхронизируй мои чаты и покажи план задач. Потом прочитай сегодняшние новые сообщения в личных чатах и в группах с тегом watch-tasks и добавь задачу на каждую просьбу или обещание, которые пропустили правила; если это обещание отправителя, укажи его исполнителем. Покажи список, прежде чем что-то добавлять. Ничего не отправляй.
```

- **agenda** показывает просроченные задачи, задачи со скорым сроком или пора проверить, затем чаты,
  где ответа ждут от вас, и чаты, где ждёте вы, затем то, что должны вам: открытые задачи с исполнителем,
  сначала самые старые. Предупреждает, если хранилище давно ничего не сохраняло.
- **add** требует тип и категорию (`--category`) и
  отказывает, если уже есть похожая задача; см. [Без дубликатов](#без-дубликатов).
- **plan** задаёт название, описание, срок, следующую проверку и исполнителей. Следующая проверка — когда агенту
  стоит снова посмотреть на задачу; вам она не напоминает.
- **link** привязывает к задаче сообщения, чаты, людей, документы, заметки или адреса.
- **show** показывает одну задачу с планом и всем, что к ней привязано.
- **scan** запускает правила задач на последних сохранённых сообщениях чата и показывает задачи,
  которые они откроют. Открывает их только с `--yes`. См.
  [Задачи из истории чата](#задачи-из-истории-чата).
- **close** закрывает задачу как `done` или `dismissed`. Закрытая задача остаётся закрытой. Открыть
  её снова может только `tasks unmerge`, и только если задачу закрыло объединение. Закрытие агентом
  может ждать вас; см. [Когда задачу закрывает агент](#когда-задачу-закрывает-агент).
- **reject** отклоняет закрытие, которое предложил агент. Задача остаётся открытой.

## Отношения между задачами

Одна задача проекта может ждать другую (`blocked-by`), продолжать её (`follow-up-of`) или просто быть
с ней связана по смыслу (`related-to`). Такие отношения устанавливаете только вы; агент может их
предложить. Они работают между задачами проектов в `memo`: см.
[Что делать в первую очередь](./memo/tasks.md#что-делать-в-первую-очередь).

`follow-up-of` инструмент пишет и сам, между задачами из сообщений: новая задача о задаче, закрытой
за последние 14 дней, связывается с ней как продолжение (см. [Без дубликатов](#без-дубликатов)).
В `tg` и `max` `tasks show` для закрытой задачи также называет задачу, которая её продолжает.

Есть ещё два вида. `duplicate-of` говорит, что задача — то же дело, что и другая. Его записывает
объединение, и он связывает задачи из сообщений одного аккаунта. `discovered-from` говорит, что
задача нашлась во время работы над другой.

## Как агент работает с задачами после синхронизации

1. Агент загружает новые сообщения (`messages sync`). Синхронизация запускает правила задач на
   сохранённом, с того места, где остановился прошлый запуск. Первый запуск читает только чаты с
   сообщениями за последние 14 дней. В `tg` и `max` первый запуск к тому же не открывает задач из этих
   сообщений: ответ считает задачи, которые он отложил, и называет `tasks scan`. Следующая синхронизация пропускает чат, где ничего нового не отправляли, поэтому загруженные ею старые
   сообщения не открывают задач. В ответе сказано, сколько задач открыто, сколько закрыто и сколько
   пар ушло в список на проверку.
2. Читает план и сверяет каждую новую задачу с её сообщениями.
3. Задаёт название, срок и правильную категорию, привязывает сообщения, которые относятся к одному
   делу, и закрывает сделанное. Если агент не уверен, что задача сделана, его закрытие ждёт вас.
4. Проходит по списку возможных дубликатов (см. ниже).
5. Показывает вам, что изменил, и спрашивает, прежде чем что-либо уйдёт с компьютера.

## Задачи из истории чата

Первая синхронизация аккаунта в `tg` и `max` читает вашу историю, но не открывает из неё задач: на старые
вопросы часто уже ответили в другом месте, или они больше не важны. Вы сами решаете, ради каких чатов
стоит это делать.

1. Спросите агента, какие задачи откроет история чата. Он запускает `tasks scan` с этим чатом, и
   команда читает 50 последних сохранённых сообщений (`--last` — до 1000). В ответе для каждой задачи
   указаны тип, категория и сообщение. Ничего не меняется.
2. Проверьте список. Если вы согласны, агент запускает ту же команду с `--yes`. Задачи открываются
   через проверку на дубликаты, как при синхронизации, а открытая задача по вопросу, на который вы
   уже ответили, закрывается.

Проверка идёт по тем же правилам, что и синхронизация: канал не открывает ничего, а группа —
только то, что спрашивают у вас, если вы не поставили ей тег `watch-tasks`. `tasks scan` читает только
сообщения, сохранённые на вашем компьютере, и ничего не отправляет. У агентов, которые работают через
MCP-сервер, есть такой же инструмент, `tasks_scan`, с `yes` вместо `--yes`.

Если вы хотите, чтобы первая синхронизация открывала задачи из истории, команда
`config set task_first_pass_per_chat <n>` разрешает ей открыть до n задач на чат, начиная с самых
новых (по умолчанию 0, не больше 1000). Эта настройка действует на всё хранилище, как настройки из раздела
[Когда задачу закрывает агент](#когда-задачу-закрывает-агент).

```text
tasks scan "Renovation"
tasks scan "Renovation" --last 300 --yes
config set task_first_pass_per_chat 20
config unset task_first_pass_per_chat
```

## Когда задачу закрывает агент

Это поддерживают `tg` и `max`. В `memo` закрытие агентом по-прежнему закрывает задачу.

Агент, который закрывает задачу, указывает, насколько он уверен, что больше ничего не нужно, числом от
0 до 1 (`--certainty`). Если уверенность не ниже порога хранилища (по умолчанию 0.8), задача
закрывается. Ниже — задача остаётся открытой с предложением закрыть: какой агент его сделал, насколько
был уверен и почему. План задач показывает такие задачи, а `tasks list close:suggested` находит их. Вы
подтверждаете предложение командой `tasks close <task>` или отклоняете командой `tasks reject <task>`;
позже агент может снова предложить закрыть задачу. Закрытие нельзя отменить, поэтому неуверенное ждёт
вас.

Этим управляют две настройки всего хранилища: `task_agent_close` (по умолчанию `on`; `off` делает
любое закрытие агентом предложением) и `task_agent_close_min` (по умолчанию 0.8).

Что инструмент запустил агент, видно по переменной окружения `AI_AGENT` или `CLAUDECODE`. Закрытие
агентом без `--certainty` отклоняется с ошибкой `task.certainty-required`. Если закрыть задачу
попросили вы, агент закрывает её от вашего имени с `--as-owner`. Правило, которое закрывает вопрос,
когда вы ответили в чате, — не закрытие агентом, и уверенность ему не нужна.

```text
tasks close REQ-22 --as done --certainty 0.9 --reason "invoice sent"
tasks list close:suggested
tasks close REQ-22
tasks reject REQ-22
config set task_agent_close_min 0.9
config set task_agent_close off
```

## Без дубликатов

Одна и та же просьба часто приходит несколькими сообщениями: «пришлёшь счёт?», потом «счёт на 15 000,
пожалуйста», потом напоминание через два дня. Это должна быть одна задача. Инструмент проверяет
каждую новую задачу до того, как создать её:

- **Уверен, что это та же задача:** так бывает, только когда у того же сообщения уже есть задача
  этого типа. Правило также не открывает задачу для сообщения, привязанного к задаче как `evidence`.
  Новая задача не создаётся, а в ответе показана та задача.
- **Не уверен:** инструмент не гадает. Если задачу добавляет агент, `tasks add` отказывает и
  показывает до пяти похожих задач с причинами («тот же человек, та же сумма»). Агент повторяет
  команду с `--into <task>`, чтобы привязать сообщение к одной из них, или с `--new`, чтобы создать
  новую задачу. Если задачу нашло правило, задача создаётся, а похожие пары попадают в список на
  проверку.
- **Явно другая:** создаётся новая задача.
- **Похожа на задачу, закрытую за последние 14 дней:** создаётся новая задача, связанная
  `follow-up-of` с закрытой. Закрытая остаётся закрытой. `tasks add` отказывает, только пока той же
  работой может быть открытая задача.

Проверка сравнивает слова (в том числе другие формы слова и опечатки), человека, сумму денег, срок,
категорию, ответы и время. В `tg` и `max` время — это когда были отправлены сообщения задач, а не когда
задачи записаны, поэтому задачи, записанные из истории за один раз, не выглядят похожими. В `tg` и `max` две
задачи из одного сообщения, например обещание и просьба из одного длинного сообщения, сравниваются
только по своим названиям и описаниям: общее сообщение ничего не говорит о том, одно ли это дело. Она читает название и описание задачи, её исходное сообщение и 5 новейших
привязанных сообщений, поэтому задача, которую правило открыло с пустым названием, сравнивается по
своему сообщению. Сроки она читает на английском, русском и испанском, например `by Friday`,
`до пятницы` или `el viernes`. Один только общий чат никогда не делает две задачи «одной».
**Инструмент никогда не объединяет задачи только по оценке.** Некоторые похожие задачи, например
подарок маме и подарок папе на ту же сумму, отличаются смыслом одного слова, поэтому решает агент или
вы.

**Кто решает.** Список на проверку разбирает агент, который просматривает ваши чаты после
синхронизации. Он объединяет пары об одном деле и отклоняет пары о разных. Если он не может решить,
он отмечает пару как неясную. Вы видите только неясные пары: `tasks duplicates list decision:unsure`.

Когда вы или агент привязываете сообщение к задаче (`tasks link`, `tasks add --into` или
`tasks merge`), проверка снова запускается для этой задачи. Новые возможные пары попадают в список на
проверку. Привязка остаётся в любом случае.

Объединение привязывает все сообщения дубликата к оставшейся задаче и закрывает дубликат как
`dismissed` с отношением `duplicate-of`. **Объединение можно отменить**, и ничего не удаляется.
Отклонённая пара больше не возвращается.

```text
tasks related REQ-23
tasks duplicates list
tasks merge REQ-23 --into REQ-22
tasks duplicates reject REQ-23 REQ-22
tasks duplicates defer REQ-23 REQ-22
tasks duplicates list decision:unsure
tasks unmerge REQ-23
```

`tasks related` показывает задачи, которые могут быть тем же делом, что и данная, — лучшие первыми,
каждую с полосой (`likely`, `maybe` или `different`) и причинами. Команда ничего не меняет.

## Категории, теги и ключи

- **Категория** говорит, о чём задача. В списке по умолчанию 59 категорий: сначала узкие, например
  `taxes`, `bills`, `health`, `travel` и `fitness`, за ними широкие, например `money`, `documents` и
  `meeting`, а в конце `work`, `personal` и `other`. `tasks categories` печатает каждую с её смыслом и
  словами. `tasks add` требует категорию и отказывает, если такого имени нет в списке. Правило
  выбирает категорию по словам сообщения, из двух подходящих — более узкую (счёт за коммунальные
  услуги — `bills`, а не `money`), или `other`, если ни одно слово не подошло; агент исправляет её
  через `tasks update --category`.
- **Один список в общем файле настроек.** `tg` и `max` читают ваши изменения списка из
  `~/.config/WireCat/config.json`, раздел `task_categories`. Это не файл настроек профиля, поэтому
  список одинаков во всех профилях, а «финансы» и «платежи» не появятся рядом. `memo` пока не читает
  этот файл. Он берёт список, сохранённый в хранилище, или свой список по умолчанию, в котором пока
  прежние семь категорий (`money`, `documents`, `meeting`, `delivery`, `access`, `personal` и `other`).
- **Список можно менять.** У каждой категории есть смысл и слова, по которым её выбирает правило.
  Слово совпадает и с другими своими формами; слово может указать свой язык, например `es:vuelo`, и
  тогда испанское слово вроде `es:pagar` совпадает и с `pagues` в испанском сообщении. Можно добавить
  или изменить категорию, удалить её или вернуть список по умолчанию; в списке до 80 категорий.
  `other` удалить нельзя. В файле только ваши изменения, поэтому категории, которые добавит следующий
  выпуск, всё равно появятся. `tasks categories` называет файл в `file`, а `config show` отмечает
  категории, которые взяты из него. Файл с неверным JSON или с неверной категорией отклоняется с
  указанием его пути.
- **Список из хранилища переходит в файл.** Список, который `tg` сохранил в хранилище до перехода на
  файл, по-прежнему действует. Следующая `config set` или `config unset` для категории переносит его в
  файл и убирает из хранилища; после этого `memo` снова берёт свой список по умолчанию.
  `config unset task_categories` убирает раздел из файла и даёт текущий список по умолчанию.
- **Категория, которой нет в списке.** Задачи сохраняют свою категорию, когда её убирают из списка.
  `tasks categories` называет такие категории в разделе `unlisted`, с числом открытых задач и всего, а
  `tasks agenda` называет те, что ещё стоят у открытых задач (`unlisted_categories`). Их задачи находит
  `tasks list category:<name>`, а переносит одну `tasks update <task> --category <name>`.
- **Теги** вроде `urgent` или `waiting-for-them` работают и на задачах: `tags add urgent --task REQ-22`.
  Теги нужны только для фильтров; проверка на дубликаты их не учитывает.
- **Ключи по типам:** задача из сообщения получает короткий ключ, например `Q-15` для вопроса,
  `REQ-22` для просьбы, `M-7` для упоминания или `PR-4` для обещания. Ключ никогда не меняется, его
  можно цитировать в чате или заметке. Старые задачи сохраняют свой ключ, например
  `IN1A2B3C4D-17`; работают оба вида ключей и полный id.

```text
tasks add msg:telegram/1/77/42 --type request --category money
tasks categories
tasks agenda category:money tag:urgent
tasks list category:money
tasks update REQ-22 --category bills
config set task_categories.travel "trips and tickets | flight, hotel, es:vuelo"
config unset task_categories.travel
config unset task_categories
config show
```

В `tg` и `max` файл можно править и вручную. Имя со смыслом и словами добавляет или заменяет категорию, а
`null` убирает категорию из списка по умолчанию:

```json
{
  "task_categories": {
    "garden": "plants | seedling, es:planta",
    "religion": null
  }
}
```

Команды `config set task_categories…` и `config unset task_categories…` пишут в тот же файл и
сохраняют его другие разделы. Ни одна команда `config` на этой странице не меняет один профиль:
настройки из раздела [Когда задачу закрывает агент](#когда-задачу-закрывает-агент) и
`task_first_pass_per_chat` остаются в хранилище.

## Бронь задачи

Когда одновременно работают два агента или агент и вы, один из них сначала бронирует задачу. Бронь
заканчивается сама через 30 минут, поэтому остановившийся агент не держит задачу вечно. Повторная
бронь продлевает вашу. Закрытие задачи снимает бронь. План задач показывает, кто держит каждую
задачу, и скрывает задачи, которые забронировал кто-то другой; `tasks agenda claimed:any` показывает и
их. Вы, владелец, можете снять любую бронь.

Держатель брони — одна сессия агента. Инструмент берёт первое, что задано:

1. `--holder <name>`
2. переменная окружения `WIRECAT_HOLDER`
3. `claude-code:<session id>` из переменной `CLAUDE_CODE_SESSION_ID`, которую задаёт Claude Code
4. имя агента из переменной `AI_AGENT`
5. `owner`

Агент без переменной сессии, например веб-агент, передаёт id своего чата через `--holder`.

```text
tasks claim REQ-22 --lease 30m
tasks release REQ-22
tasks agenda claimed:any
```

У агентов, которые работают через MCP-сервер, есть те же инструменты, например `tasks_claim`,
`tasks_release`, `tasks_categories`, `tasks_related`, `tasks_duplicates`, `tasks_merge` и `tasks_unmerge`.
В `tg` и `max` `tasks_close` требует `certainty`, как и `tasks close` от агента. `tasks_scan`
строит задачи чата из его истории.
