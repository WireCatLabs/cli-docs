Вы пишете инструмент командной строки или интеграцию для агента, которая читает или пишет общее хранилище WireCat. За
пять минут эта страница даёт вам модель: какие бывают записи, как они связаны и какие правила не дают вашему инструменту
сломать другие. Ниже показано, как добавить источник и хранить свои данные. Дальше —
[вход в сервис и соответствие стандартам](./build-sign-in.md).

## Общее хранилище

Каждый инструмент WireCat хранит данные в одном файле SQLite на компьютере владельца — `wirecat.db`. Этим файлом владеет
пакет `@wirecat/cli-core`: его таблицы, миграции и код, который их читает и пишет. Инструмент обращается к файлу только
через cli-core и никогда — своим SQL ([правила хранилища](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/store.md)).

## Сущности и записи источников

- **Сущность** — это то, что владелец имеет в виду на самом деле: человек, событие, документ. В ней нет id провайдера.
- **Запись источника** — то, что о сущности знает один источник: пользователь Telegram, адрес почты, встреча Zoom,
  запись календаря, файл Drive. В ней есть аккаунт, откуда она пришла, и собственный id провайдера.

Одна сущность собирает записи из нескольких источников. Одна встреча в Zoom и в двух календарях — одно событие. Один
человек в Telegram и в почте — один человек. Ваш инструмент пишет записи источников; cli-core связывает их с сущностями.

## `external_id`

Id, который провайдер дал записи, хранится в `external_id` и уникален в пределах аккаунта. Второй id, который провайдер
тоже использует, получает свою именованную колонку, например `ical_uid`. Никогда не колонка с именем провайдера и
никогда не только внутри `metadata` ([WC-DATA-3](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-3--a-providers-id-goes-in-external_id)).

## Связи

Связь записи источника с её сущностью помнит, как она создана, насколько надёжна, кто и когда её сделал. Каждое
изменение пишется в журнал, поэтому ошибочную связь можно отменить. Везде действуют три правила:

1. Связь, сделанную владельцем, никогда не заменяет автоматическая.
2. Два одинаково подходящих кандидата не дают связи.
3. Совпадение названия или пересечение по времени само по себе никогда не связывает две записи.

Это правило [WC-DATA-6](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-6--every-link-records-how-it-was-made-the-owners-link-wins-ambiguity-makes-no-link).
Как связи выглядят для читателя — на странице [Как всё связано](./how-things-are-linked.md).

## Общие сущности и ваши таблицы

Запись, которая может понадобиться не одному инструменту, — **общая сущность**: её таблица живёт в cli-core. Таблица,
нужная только вашему инструменту, — контрольная точка синхронизации, кэш — живёт в собственном файле SQLite вашего
инструмента, и другие инструменты её не читают
([WC-DATA-1](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-1--a-record-more-than-one-tool-needs-is-a-core-entity-in-cli-core-a-clis-own-tables-stay-private)).
Подробнее — [Хранить свои данные](./build-concepts.md#хранить-свои-данные).

## Ещё в хранилище

- **Реестр провайдеров.** Ваш инструмент при каждом запуске записывает своего провайдера (имя, вид, псевдонимы,
  команду) в хранилище, и все остальные инструменты узнают о новом источнике без выпуска cli-core. Строки провайдера,
  которого ни один инструмент не записал, пропускаются с пояснением и никогда не ищутся как сообщения. См.
  [Добавить источник](./build-concepts.md#добавить-источник).
- **Список на проверку.** Пары, которые инструменты не могут различить, например два события для одной встречи, ждут там
  решения владельца.
- **Записи календаря и файлы** — записи источников для событий и документов, а у каждой учётной записи может быть адрес
  почты, чтобы один адрес объединял одного человека.

## Что сломается, если это пропустить

Id провайдера только в `metadata` нельзя обновить по ключу, и каждая синхронизация создаёт дубль. Связь по одному
названию соединяет две разные встречи, и владелец видит чужую запись. SQL к общему файлу ломается на следующей миграции
cli-core.

Дальше: [Добавить источник](./build-concepts.md#добавить-источник).

## Добавить источник

У вас есть сервис — календарь, приложение для встреч, хранилище файлов, — и вы хотите, чтобы его записи были в общем
хранилище WireCat и ими пользовались поиск и все остальные инструменты. Эта страница показывает шаги: выбрать сущность,
которую питают ваши записи, записать их как записи источников, дать cli-core их связать и не пустить внутрь секреты.
Она предполагает, что вы знаете [основы](./build-concepts.md).

### Шаги

1. **Выберите сущность.** Решите, что владелец имеет в виду под вашими записями: человека, событие или документ. Ваши
   записи — записи источников этой сущности. Если ничего не подходит, это новая общая сущность, и она требует изменения
   в cli-core, а не своей таблицы.
2. **Пишите через cli-core.** Сохраняйте записи через области хранилища cli-core и никогда своим SQL
   ([WC-STORE-5](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/store.md#wc-store-5--a-cli-writes-no-sql-against-the-shared-store)).
   Если в области нет нужного метода, добавьте его в cli-core вместе с тестом.
3. **Ключ — id провайдера.** У каждой записи есть `account_id` и id провайдера в `external_id`. Повторное сохранение
   той же записи обновляет её, а не добавляет копию.
4. **Используйте стандартные имена.** Поле, по которому фильтруют, сортируют, соединяют или которое показывают в списке,
   — колонка со стандартным именем: `title`, `url`, `starts_at`, `ends_at`, `external_updated_at`. Время — в
   миллисекундах UTC. Всё остальное — в `metadata`, по списку разрешённых полей
   ([WC-DATA-4](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-4--use-the-standard-field-names),
   [WC-DATA-5](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-5--a-field-the-store-filters-sorts-joins-or-lists-on-is-a-column-the-rest-is-allow-listed-json)).
5. **Дайте сопоставлению их связать.** cli-core связывает вашу запись с сущностью по правилу: тот же ключ, общий id
   вроде `ical_uid` календаря, ссылка для входа или точный хеш содержимого. Два равных кандидата не дают связи.
6. **Мягко удаляйте то, что исчезло.** Когда провайдер перестаёт возвращать запись, она получает `deleted_at`. Её
   сущность и связи владельца остаются
   ([WC-DATA-7](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-7--a-source-record-the-provider-stops-returning-is-soft-deleted-its-entity-and-links-stay)).

### Пример: встречи Zoom

Инструмент `zm` уже сейчас так переносит встречи Zoom в хранилище:

- каждая встреча — строка `meetings`, запись источника, сохранённая через хранилище встреч cli-core;
- `account_id` — аккаунт Zoom, `external_id` — id встречи в Zoom, вместе они уникальны;
- `event_id` указывает на событие — сущность — и выставляется при связывании событий;
- участники — учётные записи, поэтому участник Zoom и тот же человек в Telegram могут сойтись в одном человеке.

Запись разговора, пришедшая позже, находит ту же строку по ключу и обновляет её.

### Никогда не хранить

- токены, пароли и ключи ([правила безопасности](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/security.md));
- коды доступа к встречам, PIN-коды и параметры запроса в ссылке для входа;
- сырой ответ провайдера; храните только разрешённые поля.

### Зарегистрируйте провайдера

При каждом запуске ваш инструмент записывает своего провайдера в хранилище: имя, вид, псевдонимы и команду. Тогда все
остальные инструменты узнают о новом источнике без выпуска cli-core. Строки провайдера, которого ни один инструмент не
записал, пропускаются с пояснением и никогда не ищутся как сообщения.

```ts
import { openStore } from "@wirecat/cli-core/store"

const store = await openStore()
await store.accounts.registerProvider({ name: "acme", kind: "meetings", aliases: ["acme"], command: "acme" })
```

`kind` — как поиск читает ваши записи: `messages`, `mail`, `notes`, `documents`, `meetings` или `events`.

### Что сломается, если это пропустить

Без `external_id` каждая синхронизация добавляет ту же запись снова. Без мягкого удаления неудачная синхронизация стирает
то, что владелец связал или написал. Без общих областей хранилища следующая миграция cli-core ломает ваш инструмент.

Дальше: [Хранить свои данные](./build-concepts.md#хранить-свои-данные).

## Хранить свои данные

Вашему инструменту нужны таблицы, которыми пользуется только он: контрольная точка синхронизации, кэш, служебные данные
провайдера. Эта страница показывает, где они живут и как ссылаются на общее хранилище, чтобы cli-core мог менять свою
схему, не ломая ваш инструмент, и чтобы другие инструменты не начали зависеть от ваших внутренних таблиц.

### Правило

- Таблица, нужная только вашему инструменту, живёт в **собственном файле SQLite вашего инструмента** рядом с общим
  хранилищем.
- Ваш инструмент сам выполняет миграции этого файла.
- Ваши таблицы ссылаются на общие записи **только по id**, например по id аккаунта или документа.
- Другие инструменты не открывают ваш файл, а ваш инструмент не открывает чужие.

Это правило [WC-DATA-1](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/data-model.md#wc-data-1--a-record-more-than-one-tool-needs-is-a-core-entity-in-cli-core-a-clis-own-tables-stay-private).
Если те же записи нужны второму инструменту, это общая сущность, и ей место в cli-core.

### Шаги

1. Найдите папку общего хранилища через `storePath` из `@wirecat/cli-core/store`. Она учитывает `MESSAGING_STORE`,
   поэтому тесты, которые переносят общее хранилище, переносят и ваш файл.
2. Откройте свой файл в этой папке через `openCache` из того же модуля. Он выбирает SQLite среды выполнения (Node или
   Bun) и ставит те же настройки, что у общего хранилища.
3. Создавайте и меняйте свои таблицы миграциями, которые идут только вперёд: добавлять, никогда не править и не
   пересоздавать ([WC-STORE-7](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/store.md#wc-store-7--migrations-only-go-forward-add-never-edit-or-rebuild)).

### Пример

Инструмент `acme-cli` хранит одну контрольную точку синхронизации на аккаунт:

```ts
import { dirname, join } from "node:path"
import { openCache, storePath } from "@wirecat/cli-core/store"

const own = await openCache(join(dirname(storePath()), "acme-cli.db"))
own.exec(`CREATE TABLE IF NOT EXISTS sync_checkpoints (
  account_id INTEGER PRIMARY KEY,
  cursor TEXT NOT NULL,
  updated_at INTEGER NOT NULL
)`)
```

`account_id` — id строки аккаунта в общем хранилище. Контрольная точка не копирует имя или провайдера аккаунта; она
читает их из cli-core, когда они нужны.

### Скоро

Помощник в cli-core, который открывает собственный файл инструмента и выполняет его миграции, стоит в списке «позже».
Пока его нет, используйте `openCache`, как выше.

### Что сломается, если это пропустить

Своя таблица внутри общего хранилища ломается при миграции cli-core, и её начинают читать другие инструменты. Копия
общего поля в вашей таблице устаревает, когда владелец меняет оригинал. Чужой инструмент, открывший ваш файл, ломается
при вашем следующем изменении.
