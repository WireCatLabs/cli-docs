Вам нужен инструмент командной строки для сервиса — календаря, заметок, чата, — которым пользуются и люди, и
ИИ-агенты и который работает вместе с другими инструментами WireCat. Быстрее всего начать с шаблона. Эта страница
показывает старт, что WireCat даёт вашему инструменту, шаги вкратце, а затем объясняет, почему всё устроено так.

## Начните с шаблона

[cli-template](https://github.com/WireCatLabs/cli-template) создаёт рабочий каркас: общие команды, настройки,
руководство для агента и MCP-сервер работают, и все проверки стандартов WireCat проходят. Шаблон задаёт несколько
вопросов о сервисе и записывает ответы в файл дизайна для вас или вашего агента.

```sh
git clone https://github.com/WireCatLabs/cli-template.git
cd cli-template && pnpm install && pnpm kit:build && cd ..
node cli-template/kit/dist/main.js new acme-cli --command acme --package @example/acme-cli --owner example
cd acme-cli && pnpm install && pnpm build
node dist/bin/acme.js personal doctor
```

`personal` — это профиль: имя одного аккаунта. Каждая команда, которая работает с аккаунтом, начинается с него;
профиль никогда не подставляется сам.

`new` печатает шаги, которые нужно сделать человеку: создать репозиторий, настроить публикацию в npm, выбрать день
для ежемесячных проверок. Затем передайте `docs/dev/DESIGN.md` своему агенту и пишите инструмент.

## Что WireCat даёт вашему инструменту

- **Одно общее хранилище и поиск.** Ваши записи лежат рядом с сообщениями, письмами, встречами и документами других
  инструментов, и memo ищет по всем сразу.
- **MCP-сервер для агентов.** Агенту доступна каждая команда, включая запись, под ключами разрешений профиля.
- **Правильная работа с аккаунтами.** Профиль всегда указан явно, а чтение по нескольким аккаунтам охватывает их все.
- **Вход и секреты.** Токены хранятся в системной связке ключей и никогда не попадают в вывод и логи.
- **Проверки, которые держат вас в рамках стандартов.** `cli-dev lint`, общие правила линтера и проверки выпуска
  приходят вместе с шаблоном.

## Как его написать, вкратце

1. **Опишите сервис.** Ответьте на вопросы в `docs/dev/DESIGN.md`: что хранит сервис, как в него входят, что нельзя
   сохранять никогда.
2. **Напишите адаптер.** Одна часть кода говорит с сервисом и превращает его объекты в типы вашего инструмента.
3. **Сохраняйте записи источника.** Сохраняйте ответы сервиса через cli-core, с идентификатором сервиса в
   `external_id`. cli-core свяжет их с людьми, событиями и документами, которые уже знают другие инструменты. См.
   [Добавить источник](./build-add-source.md).
4. **Держите свои таблицы отдельно.** Точки синхронизации и кэши лежат в собственном файле инструмента. См.
   [Хранить свои данные](./build-own-data.md).
5. **Называйте команды общими словами.** `list`, `show`, `search`, те же флаги, что у всех инструментов;
   `cli-dev lint` подскажет, если имя не подходит.
6. **Выпустите.** `pnpm release:check` запускает все проверки, которых требуют стандарты. См.
   [Соответствовать стандартам и обновляться](./build-stay-compliant.md).

## Почему всё устроено так

**Одно хранилище — значит, ответы охватывают все инструменты.** Вопросу «что мы решили про запуск?» нужны чат,
почта и заметки встречи вместе. Это работает, только когда каждый инструмент пишет в одно хранилище с одинаковыми
именами полей.

**Записи источников и сущности — значит, ничего не считается дважды.** Одна встреча приходит из двух календарей и из
Zoom. Каждая копия — запись источника; встреча — одна сущность. Если инструменты не могут различить двух кандидатов,
они не создают связь и спрашивают владельца. Ошибочное слияние хуже дубля. Модель описана на странице
[Основы за пять минут](./build-concepts.md).

**Явный профиль — значит, ни одна команда не затронет чужой аккаунт.** Инструмент, который берёт «первый аккаунт»,
рано или поздно отправит рабочее сообщение с личного аккаунта. Без профиля команда завершается ошибкой со списком
вариантов.

**Каждая команда через MCP, под разрешениями — значит, агенты могут делать настоящую работу безопасно.** Агент
получает те же команды, что и человек. Что можно запускать, владелец решает ключами разрешений, и каждая запись
попадает в журнал.

**Общие стандарты — значит, ядро может меняться, не ломая вас.** Правила собраны в одном
[справочнике](https://github.com/WireCatLabs/cli-base/blob/main/docs/standards/README.md), и большую часть из них
проверяют машины. Инструмент, который им следует, продолжает работать, когда меняется cli-core, а команда шаблона
`upgrade` приносит в ваш инструмент его последующие изменения.
