Наши CLI ищут по архиву мессенджера на компьютере самого владельца. `search messages --discover` находит
кандидатов по смыслу и по словам, а потом небольшая модель-переранжировщик (mMARCO, 8 бит) читает первые
50 и расставляет их по порядку. Когда переранжировщик включили по умолчанию, `--discover` на настоящем
архиве замедлился с 1,9 до 5,1 с. Вот четыре шага, которые мы сделали, и чему научил каждый.

## Акт первый: пакеты изменили ответы, а не скорость

Очевидное решение — оценивать 50 пар пакетами: один прогон модели на много пар вместо прогона на каждую.
В WebAssembly это сэкономило не больше 15%, и только когда пары отсортированы по длине. Пары разной длины
шли медленнее: каждую дополняют до самой длинной, и дополнение стоит столько же, сколько текст.

Хуже того, оценки поплыли. Одна и та же пара получила 0,04 одна, 0,48 с дополнением до 200 токенов и 0,34
рядом с другой парой. 8-битная модель, вероятно, подбирает свой диапазон по всему входу каждого
прогона, поэтому соседи по пакету меняют оценку пары. Порядок, который зависит от того, какие результаты
попали в один пакет, — это не порядок. Мы оставили одну пару на прогон.

| Оценка 50 пар разной длины | Время | Наибольшее изменение оценки |
| --- | ---: | ---: |
| По одной | 1,54 с | — |
| Пакеты по 5, по длине | 1,33 с | 1,01 |
| Один пакет из 50 | 2,37 с | 0,85 |

## Акт второй: натив быстрее в 2 раза, а не в 10

Затем мы запустили те же модели через нативную библиотеку ONNX Runtime вместо её сборки для WebAssembly.
Замер на коротком тексте обещал ускорение в 4–10 раз. На настоящем архиве `--discover` ускорился с 4,58
до 3,20 с, и в обоих случаях прямой ответ был в первой пятёрке у 6 из 6 известных вопросов.

Разница — в длине входа. Настоящий вход переранжировщика несёт чат, автора, дату и сообщение, на которое
ответили: медиана 153 токена, и каждый десятый длиннее 762. В синтетическом наборе медиана была 48. На
одну пару натив был быстрее в 2–2,5 раза. Замеры на коротком тексте завышают выигрыш для длинного.

Позже мы обрезали сообщение, на которое ответили, до 300 знаков (это отдельный пост). С обоими
изменениями выпущенный CLI выполнял `--discover` за 2,91 с нативно против 4,10 с через WebAssembly.

## Акт третий: без новых пакетов

Обычно нативную библиотеку поставляют пользователям npm отдельным пакетом на каждую платформу. Мы не
хотели публиковать пять новых пакетов и раздувать установку у тех, кто никогда не скачивает модели.

В npm-пакете `onnxruntime-node` на каждую платформу две части: связка на 0,4 МБ
(`onnxruntime_binding.node`) и сама библиотека. Связка ищет библиотеку в своей же папке. Поэтому связки
едут внутри пакета, который мы уже публикуем, а библиотека скачивается вместе с моделями из официального
архива выпуска Microsoft и сверяется с закреплённым хешем sha256. Поиск сам ничего не скачивает:
библиотека появляется, только когда пользователь запускает `models download`. Если её нет или она не
загружается, модели работают через WebAssembly, как раньше. На 450 парах оценки точно совпали с
библиотекой из самого npm-пакета.

## Акт четвёртый: библиотека для Windows была только внутри npm-архива

В Windows тот же приём не сработал. Связка для Windows берёт одну функцию из `onnxruntime.dll` по номеру, а
не по имени: порядковый номер 4, функцию настройки DirectML — слоя Windows для видеокарты. В выпуске
Microsoft лежит обычная сборка DLL, без этой функции, поэтому связка отказывалась её загружать.

Сборки 1.30.0 с DirectML нет ни в архиве выпуска Microsoft, ни в NuGet — там она кончается на более
старой версии. Мы нашли её в одном месте: внутри собственного npm-архива `onnxruntime-node` на 113,5 МБ.
Поэтому в Windows `models download` один раз скачивает этот архив, оставляет одну DLL и сверяет её со
своим закреплённым хешем. Часть DirectML загружается, только если она нужна.

Потом мы проверили это по-настоящему. Новый процесс в CI скачивает библиотеку и запускает две крошечные
тестовые модели нативно на Linux x64 и arm64, macOS на Apple silicon, Windows x64 и Windows arm64. Ещё он
проверяет, что Alpine Linux, для которого сборки нет, ничего не предлагается и он остаётся на
WebAssembly. Все шесть проходят; задания в Windows занимают 1,5–2 минуты.

## Что мы бы сказали тому, кто делает то же

- Мерьте на настоящей длине входа. Короткий синтетический текст показывал нативную библиотеку до пяти раз
  лучше, чем она есть.
- Не обрабатывайте пакетами модель с динамическим квантованием, если оценки разных пар должны быть
  сравнимы.
- Нативную библиотеку можно скачивать по требованию, с закреплённым хешем и WebAssembly как запасным
  вариантом. Пакет на каждую платформу может и не понадобиться.
- Проверяйте библиотеку на каждой системе в CI. Прочитать список файлов пакета — не то же самое, что её
  загрузить.
