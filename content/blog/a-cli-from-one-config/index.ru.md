Я сделал так, что новый CLI в WireCat собирается из одного файла. Вы пишете `wirecat.config.ts` - что это за сервис, где лежит описание его API, как проверить токен и какие поля в ответах это люди, компании и сделки. Дальше одна команда `new --from-config` делает CLI с синком в локальную копию, MCP-сервером и тестами под категорию. Категорий пока 3: CRM, трекер задач и контент (посты на сайте), а описанием API может быть OpenAPI, GraphQL-схема или индекс `wp-json` сайта на WordPress.

Пишу это в первую очередь для тех, у кого в компании своя CRM или хелпдеск, и хочется, чтобы агент работал с ней так же, как с почтой и чатами в WireCat. Сразу скажу, где граница: CRM из конфига пока только читает, а хелпдеск, у которого есть только REST API, не ложится ни в одну категорию (подробнее в конце).

На конфиге уже собраны 3 настоящих CLI - attio, linear и wordpress. Собирали их агенты по шаблону, а я отвечал на их вопросы, решал, что чинить, и читал ревью. Так что время в таблицах ниже - это время работы агентов, а не мое.

До этого у шаблона ([cli-template](https://github.com/WireCatLabs/cli-template)) уже была команда `new --spec-url`: даете адрес описания API, получаете по команде на каждую операцию. Из описания PokeAPI так выходит 102 команды, настоящий ответ и рабочий MCP-сервер за 16 секунд, не считая того, что npx сначала скачивает сам шаблон. Но это только живые вызовы API. Чтобы агент быстро искал по CRM, нужна локальная копия, синк только изменений, связь людей с остальными источниками WireCat. Раньше все это писалось руками в каждом CLI.

Теперь все это описывается в конфиге, вот пример для выдуманной CRM:

```ts
import { defineCli } from "@wirecat/cli-core/manifest"

export default defineCli({
  identity: { command: "acme", package: "@acme/acme-cli", prefix: "ACME", service: "Acme CRM", owner: "acme" },
  spec: { kind: "openapi", from: "https://crm.acme.example/openapi.json" },
  auth: { preset: "token", verify: { operation: "getMe", id: "workspace.id", name: "workspace.name" } },
  category: "crm",
  source: {
    provider: "acme",
    kinds: ["person"],
    entities: {
      person: {
        list: { operation: "listContacts", query: { limit: 100 } },
        changes: { operation: "listContacts", query: { limit: 100, updated_since: "{since}" }, since: "iso" },
        get: { operation: "getContact", path: { id: "{id}" } },
        map: { externalId: "id", name: "full_name", emails: { each: "emails", value: "address" } },
      },
    },
  },
})
```

```sh
npx @wirecat/cli-template new --from-config wirecat.config.ts
cd acme-cli && pnpm install && pnpm generate
node dist/bin/acme.js work session start    # берет токен и проверяет его операцией из auth.verify
node dist/bin/acme.js work sync             # копирует записи, дальше только то, что поменялось
```

`work` тут - имя профиля, его вы выбираете сами, CLI никогда не берет аккаунт по умолчанию. Без `changes` синк тоже заработает, просто каждый раз будет перечитывать весь список. `pnpm source:check` проверяет, что каждая операция и каждый путь из `map` реально есть в сгенерированном API, так что опечатка в `full_name` всплывет еще до первого синка. Пейджинг, курсоры и локальная база, куда ложится копия, берутся из cli-core, общего пакета всех инструментов WireCat. То, что в конфиге не описать (например, сервис хранит старые значения поля рядом с текущим), пишется в `src/hooks.ts`.

Плюс вы сразу получаете тесты. Каждая операция API отправляется в фейк - поддельный сервер внутри теста, собранный из описания API. Он строгий и отказывает в любом запросе, которого описание не разрешает. А источник прогоняется через контракты категории, это общий набор тестов, которым одинаково проверяется любая CRM в WireCat. Там есть кейсы вроде "список оборвался после первой страницы, в новом запуске синк продолжает с нее, ничего не потеряно и не повторено".

## 3 CLI за 3 дня

Сам `--from-config` появился 17.11 и сначала умел только CRM. Дальше агенты сразу собирали на нем настоящие CLI, каждый находил дыры, и их чинили в шаблоне, а не в самом CLI. За 4 дня шаблон прошел путь от одной CRM до 3 категорий, и к 21.11 (версия 0.33.0) WordPress собирается из полного индекса сайта.

У всех 3 CLI `wirecat.config.ts` лежит в первом же коммите:

| | [attio-cli](https://github.com/WireCatLabs/attio-cli) | [linear-cli](https://github.com/WireCatLabs/linear-cli) | [wordpress-cli](https://github.com/WireCatLabs/wordpress-cli) |
| --- | --- | --- | --- |
| Что это | CRM, OpenAPI | трекер, GraphQL | контент, `wp-json` |
| Шаблон | 0.28.0 | 0.31.0 | 0.32.0 |
| Строк в конфиге | 64 | 102 | 117 |
| Строк в хуках | 23 | 0 | 0 |
| Кода руками после `new`, с хуками | 42 | 7 | 81 |
| Сгенерировано | 107 операций | 493 операции | 147 операций |
| От `new` до зеленого `cli-dev ready`, без живой проверки | около 2 ч 40 мин | 2 ч 54 мин | около 40 мин |
| Первый релиз | 18.11 | 19.11 | 19.11 |

`cli-dev ready` - команда, которая прогоняет все проверки перед релизом (линт, тесты, контракты, доки итд) и по каждой говорит, прошла она или нет. Живая проверка - это прогон CLI на настоящем тестовом аккаунте сервиса, ее в таблице нет.

Все цифры с первой сборки каждого CLI, из замеров в cli-testing ([attio](https://github.com/WireCatLabs/cli-testing/blob/main/performance/generation/source-manifest/README.md), [linear](https://github.com/WireCatLabs/cli-testing/blob/main/performance/generation/linear-from-config/README.md), [wordpress](https://github.com/WireCatLabs/cli-testing/blob/main/performance/generation/wordpress-from-config/README.md)). Конфиги с тех пор выросли. У attio к первому релизу добавились сделки, конфиг стал 126 строк, а хук сжался до 8.

Для сравнения, [hubspot-cli](https://github.com/WireCatLabs/hubspot-cli) тоже сделан из шаблона, но до конфига, и там 2 340 строк руками, в основном маппинг ответов HubSpot в записи CRM. Процент экономии из этого не посчитать, потому что hubspot синкает куда больше (сделки, лиды, активности итд), а attio на первой сборке только людей, компании и участников воркспейса. Порядок разницы видно, точной цифры нет.

У wordpress-cli 81 строка руками вообще не про маппинг. 10 строк - тексты, которые видит пользователь и Desktop, а 71 пришла из ревью, почти вся про ключи разрешений.

## Что сломалось на настоящем WordPress

В шаблоне был свой тестовый WordPress-кейс на 19 маршрутах, а настоящий WordPress 6.9.4 без плагинов отдает в индексе 127.

На полном индексе `pnpm generate` сразу встал. `GET /wp/v2/block-types/{namespace}` получил то же имя команды, что чтение одного типа блока, а удаление всех паролей приложений пользователя то же, что удаление одного. Теперь это `block-types-list-namespace` и `users-application-passwords-delete-all`.

Маршрут `wp_pattern_category` сломал еще больше. Для каждой операции генератор пишет ключ разрешения, и все ключи лежат в одних настройках CLI. Ключ с подчеркиванием проверка настроек не знала, и из-за этого упал не один тест, а все тесты `api`, их 151. Сейчас шаблон в своем CI собирает WordPress из всего индекса 6.9.4, а не из нарезки, чтобы такое ловилось сразу.

Дальше агент прогнал живую проверку на WordPress в Docker с 3 тестовыми пользователями: Contributor, Author и Editor. Фейки принимают любой вызов, который разрешает описание API, а настоящий сайт отказывает по ролям. Author и Contributor не могут читать теги с `context=edit`, хотя имя и слаг тега публичные, так что конфиг теперь читает их без него. Еще этим 2 ролям WordPress отвечает HTTP 400 (а внутри 403) на список страниц, и этот отказ ронял синк вообще всех постов, причем каждый следующий запуск падал на том же вызове. Сейчас для списка страниц нужно право `edit_pages`, без него вызов просто не отправляется, а синк в конце пишет, чего не хватило.

А ревью свежим агентом нашло дыру уже после того, как все проверки стали проходить. Группа `api` предлагала команду создания пароля приложения, а WordPress отдает новый пароль в ответе открытым текстом, и в индексе это поле никак не помечено как секрет. Т.е. агент мог сделать пароль и получить его в чат. В wordpress-cli это закрыли руками еще до первого пуша, а 21.11 cli-base стал помечать это поле секретом для любого WordPress CLI, и такие вызовы из `api` пропали совсем.

Там же выяснилось, что запрет на `posts create` не останавливал тот же самый вызов через `api posts-create`, и что записи, которые меняют весь сайт (плагины, настройки, пользователи), выполнялись без вопроса. Теперь перед ними CLI по умолчанию спрашивает вас.

## Время ушло не на конфиг

На сам конфиг время почти не уходило. attio агент написал за 1 ч 20 мин, после чего 17 тестов упали, и все 17 были багами общих пакетов, а не attio. Еще около 1 ч 20 мин ушло на их фиксы с ревью, плюс 2 релиза.

У linear из 2 ч 54 мин около 1 ч 55 мин ушли на общие пакеты. `cli-dev ready` не знал категорию трекера, в cli-core не было фейка, чтобы прогнать контракт трекера на источнике из конфига (это около 930 строк), а GraphQL-тест `api` падал по памяти. У Linear фильтры вложены друг в друга (`IssueFilter` доходит до `TeamFilter` и обратно), и тест, который пытался заполнить каждое необязательное поле, строил фильтр в фильтре, пока воркеру не стало плохо. Теперь все 493 операции Linear проходят где-то за 20 секунд.

Перед релизом CI требует, чтобы у каждой команды CLI и у каждого ее флага был хотя бы один тест или записанная причина, почему его нет, иначе `release:check` не пропустит версию. После ревью у linear-cli 562 таких флага и команды оставались без теста, например `--body-file` и `--all` у группы `api` или команды трекера. Эти тесты переехали в шаблон, но они покрывали трекер, а не WordPress, так что у wordpress-cli повторилось то же самое, там таких было 501. Их тоже перенесли в шаблон в тот же день.

Третий CLI собрался в разы быстрее первых двух: около 40 минут до зеленого `cli-dev ready` против 2 ч 40 мин у attio и 2 ч 54 мин у linear. До релизного коммита, с 2 ревью и живой проверкой, у wordpress ушло 1 ч 20 мин.

## Чего эти цифры не показывают

- Linear на настоящем воркспейсе в самом замере: там конфиг проверен по схеме и фейку из нее, живая проверка прошла уже потом, перед первым релизом.
- Настоящий WordPress-сайт с плагинами, кэшем или защитой, которая прячет маршруты. Все живые проверки шли на 6.9.4 в Docker.
- Сделки attio на реальных данных. В тестовом воркспейсе их нет, маппинг сделок проверен только на фейке.
- Мое время. Его я не засекал, известно только, что я ответил агентам на 3 вопроса по attio, на 1 по linear и ни на один по wordpress.
- Точное сравнение между CLI. Цифры attio сняты другим счетчиком строк, чем у linear и wordpress, и объем у всех разный, так что таблица выше показывает примерный масштаб.

## Если у вас своя CRM или хелпдеск

Что нужно, чтобы это завелось:

- Описание API - OpenAPI 3 или Swagger 2.0, в JSON или YAML, для трекера GraphQL-схема (ее `new` берет интроспекцией). Если описание местами кривое, патч с причиной идет в `scripts/spec-model.ts`. Если для списка не описан пейджинг, контрактный тест специально упадет, пока вы его не опишете.
- Вход по токену и операция, которая этим токеном читает, кто вы (`auth.verify`), потому что локальная копия хранится под этим аккаунтом. Если в вашем сервисе разные пользователи видят разные записи, я бы хранил копию отдельно для каждого пользователя, а не одну на воркспейс. В linear ревью поймало ровно это: синк одного участника мог пометить удаленными чужие приватные задачи.
- Тестовый аккаунт. Сборка и все проверки до живой проходят на фейке, но для живой проверки и реальной работы `session start` проверяет токен на настоящем сервисе.

Подойдет это пока не всем. CRM из конфига на 21.11 только читает (синк, списки, поиск по копии), а команды записи в CRM пишутся руками. Трекер поверх OpenAPI `new` отказывается делать, потому что фейк трекера в cli-core пока отвечает только на GraphQL. Т.е. хелпдеск с одним REST API сейчас не ложится ни в одну категорию из конфига, для него остается `new --spec-url` с живыми вызовами или источник руками. OAuth из конфига тоже пока не делается, его придется подключать через модуль `oauth` из cli-core. И все это только Node и TypeScript.

До того как подключать агента, я бы проверил разрешения на запись. В терминале каждая запись с уровнем `ask` спрашивает вас, а по MCP отвечать некому, так что она просто выполняется. `mcp add` поэтому не подключит профиль, который может писать, пока вы не добавите `--allow-writes`, а каждая запись потом сохраняется в `runs list`. Если профиль, который вы отдаете агенту, не должен ничего удалять в вашей CRM, поставьте `config set permissions.api readonly` или `deny` на конкретные операции. Этот абзац теперь сам пишется в README каждого нового CLI с группой `api`.

Если CLI не будет частью WireCat, в `package` идет ваш scope, в `owner` ваше имя, а как настроить репозиторий и публикацию в npm, описано в разделе [Publishing outside WireCat](https://github.com/WireCatLabs/cli-template/blob/main/kit/README.md#publishing-outside-wirecat). Все поля `wirecat.config.ts` есть в [справке по kit](https://github.com/WireCatLabs/cli-template/blob/main/kit/README.md#new-name), а как собрать свой инструмент с шаблоном и агентом и подключить его к WireCat, рассказано [в доках](/ru/docs/build-create-cli).

Следующим по плану Ghost, второй CLI для контента после WordPress. Начать со своей CRM можно прямо с примера выше: поменяйте адрес описания, операции и пути в `map` на свои и запустите `npx @wirecat/cli-template new --from-config wirecat.config.ts`.
